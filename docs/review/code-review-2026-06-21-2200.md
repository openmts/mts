# MTS 对外 API 商用化梳理

## 用户问题本质

用户希望把当前 MTS 项目的 API 从“内部研发可用”梳理成“外部用户可理解、可直接集成、可作为商用代码交付”的形态，并用 EARS 任务清单明确还需要补齐的工作和实施顺序。

## 当前公开 API 面

### Go library 根包

当前外部用户可 import 的主入口是 `github.com/openmts/mts`。

- 生命周期：`Open`、`Engine.Close`。
- 写入：`Engine.Write`、`Engine.WriteTypedBatch`、`WriteOptions`、`Point`、`TypedBatch`、`FieldValue` 与 `Float64Value`/`Int64Value`/`StringValue`/`BoolValue`。
- 查询：`NewQuery`、`QueryBuilder`、`Query`、`QueryColumns`、`QueryRows`、`QueryColumnIterator`、`QueryRowIterator`、`QueryWithExplain`、`QueryStatsSnapshot`。
- 元数据：`CreateDatabase`、`DropDatabase`、`CreateRetentionPolicy`、`ListRetentionPolicies`、`ListMeasurements`、`ListFields`、`ListSeries`。
- 运维：`Flush`、`Compact`、`CompactWithResult`、`ApplyRetention`、`MaintenanceErrors`、`StorageMemorySnapshot`、`CompactionStatsSnapshot`、`HealthSnapshot`。
- 降采样：`CreateDownsamplePolicy`、`EnableDownsamplePolicy`、`DisableDownsamplePolicy`、`DropDownsamplePolicy`、`DropDownsamplePolicyWithOptions`、`ResetDownsamplePolicy`、`ListDownsamplePolicies`、`DownsamplePolicyStatuses`、`RunDownsamplePolicy`、`RunDownsamplePolicyRange`、`RepairDownsamplePolicy`、`DryRunDownsamplePolicy`、`FromDownsamplePolicy`。

### CLI 与服务层

- `cmd/mts-storage` 提供 `check`、`repair`、`migrate`、`snapshot`、`restore`，偏本地存储维护工具。
- `internal/queryservice` 已有 `/query`、`/query/stream`、`/query/stats`、`/query/audit` 协议，但位于 `internal`，当前不能作为外部稳定 Go API 被 import。
- `internal/service` 已有 `/metrics`、`/healthz`、`/readyz`、可选 `/admin/compact` 和 pprof，但同样位于 `internal`。

## 初始商用化判断

本轮开始前，项目的核心能力已经从“存储/查询/降采样功能”层面做了大量商用补齐，现有计划文档中很多 P0/P1 项已经标记完成。但如果目标是“对外部用户提供可商用代码，以简洁易用为目标”，当时仍不能直接发布为成熟外部 API。

本轮开始前的主要短板不再是底层单机能力，而是 API 产品化：

- 根目录没有 `README.md`、`LICENSE`、`CONTRIBUTING.md`、`CHANGELOG.md`、`llms.txt`。
- 根包没有 package comment，导出类型、函数、方法几乎没有 godoc；`go doc` 只能看到符号列表，看不到使用路径、默认值、错误语义和边界。
- 没有 `ExampleXxx` 可执行示例，`go test ./... -list '^Example'` 没有发现示例。
- `Options` 直接暴露所有配置，但缺少 `DefaultOptions(path)`、`Validate` 或推荐 profile，外部用户必须读内部实现猜默认值。
- 错误契约偏薄，根包只有 `ErrInvalidQuery` 和 `ErrReadBudgetExceeded` 明确导出；很多错误对外表现依赖内部错误文本或内部包。
- 查询 Builder 已有基础表达力，但缺少面向外部用户的 typed helper、time.Time 便捷入口、聚合常量和安全默认说明。
- materialized 查询 API 与 iterator API 同时暴露，但缺少“何时用 iterator、何时用 slice API”的硬文档或保护性契约。
- HTTP 查询和运维服务虽然已有实现，但都在 `internal`，当前不是外部稳定协议。
- 根包 `types.go` 超过 300 行，公开 DTO、配置、查询、结果、降采样和转换逻辑混在一个文件里，增加 API 审查和兼容维护成本。
- 发布工程不足，缺少 API 兼容性检查、覆盖率门禁说明、版本策略和二进制发布说明。

## 本轮闭环结论

已按“Go library 先商用可用，HTTP/CLI 再产品化”的策略完成根包 API 产品化：README、godoc、示例、默认配置、错误契约、Builder 易用性、写入所有权、降采样 API、发布交付物和生产包覆盖率门禁均已落地。当前外部稳定接口边界仍限定为根包 `github.com/openmts/mts` 与 `cmd/mts-storage`，HTTP 查询与服务包保持 internal。

## 推荐实施策略

推荐按“Go library 先商用可用，HTTP/CLI 再产品化”的顺序推进。

原因：

- 当前真正稳定且外部可 import 的 API 是根包 `mts`。
- HTTP 查询和服务端点还在 `internal`，贸然外放会扩大兼容面。
- 先把根包做到 pkg.go.dev 可读、示例可跑、默认配置清晰、错误可判定，可以最短路径支持外部集成。

备选策略：

- 方案 A：只做根包文档和示例。成本最低，但默认配置、错误契约和安全保护仍弱。
- 方案 B：根包 API 产品化优先。补文档、示例、默认配置、错误契约和测试，推荐采用。
- 方案 C：同时外放 HTTP 服务 API。更接近完整产品，但会引入协议兼容、鉴权、发布和客户端 SDK 维护成本。

## EARS 实施清单

### Task 1：P0 API 发现性与快速开始

**状态:** 已实施。

**EARS:**

- When 外部用户打开仓库首页时，系统应提供简洁 README，说明 MTS 是单机嵌入式时序存储库、支持能力、明确不支持分布式和 SQL/PromQL parser。
- When 外部用户查看 pkg.go.dev 时，根包应显示 package comment、最小可运行示例和推荐使用路径。
- When 外部用户执行 `go test ./...` 时，README 中的核心示例应由 `ExampleXxx` 测试覆盖，避免文档漂移。

**实施项:**

- 新增 `README.md`，包含安装、最小写入/查询示例、Builder 查询示例、降采样示例入口、运维 CLI 简述、项目边界。
- 新增 `doc.go`，写根包 package comment。
- 新增 `example_test.go`，覆盖 `Open`、`Write`、`NewQuery`、`QueryRowIterator` 的最小路径。

**验收:**

- `go doc .` 能显示包级说明。
- `go test . -run '^Example' -count=1` 通过。
- README 不超过必要内容，保持简洁。

**实现备注:** 已新增 `README.md`、`doc.go` 和 `example_test.go`。README 覆盖安装、最小写入/查询、Builder、typed batch、降采样入口、本地维护工具和项目边界；`doc.go` 提供根包 package comment；`ExampleOpen` 与 `ExampleNewQuery` 覆盖外部 import 路径下的最小可执行示例。

**验证命令:**

- `timeout 180s go test . -run '^Example' -count=1 -timeout 3m`
- `timeout 60s go doc .`

### Task 2：P0 默认配置与配置校验

**状态:** 已实施。

**EARS:**

- When 外部用户只提供本地数据目录时，系统应能通过一个推荐默认配置打开 Engine，而不需要理解所有底层调参。
- When 配置非法时，系统应在 `Open` 前或 `Open` 早期返回稳定错误，而不是依赖内部路径上的偶发错误。
- When 用户需要面向写入、查询或小内存场景调优时，系统应提供少量清晰 profile，而不是要求直接填写全部字段。

**实施项:**

- 新增 `DefaultOptions(path string) Options`。
- 新增 `Options.Validate() error`。
- 评估是否新增 `ApplySmallMemoryDefaults` 或 `WithMemoryBudget` 一类轻量 helper；若会扩大 API，先只做 `DefaultOptions` 和文档。
- 给默认值与非法配置补测试。

**验收:**

- `DefaultOptions(t.TempDir())` 可直接 `Open`、`Write`、`Query`。
- 空 path、非法 duration、非法内存阈值有稳定错误。
- 不改变已有 `Options{}` 行为，除非单独确认 breaking change。

**实现备注:** 已新增 `DefaultOptions(path string) Options`、`Options.Validate() error` 和 `ErrInvalidOptions`。`DefaultOptions` 显式设置默认 database、retention policy、shard duration、memtable 样本阈值和基础 compaction 默认值；`Validate` 作为外部显式配置检查，不改变 `Open` 现有零值归一化行为。README 和 `ExampleOpen` 已改用 `DefaultOptions`。

**验证命令:**

- `timeout 180s go test . -run 'TestDefaultOptions|TestOptionsValidate' -count=1 -timeout 3m`

### Task 3：P0 godoc 覆盖与 API 分层整理

**状态:** 已实施。

**EARS:**

- When 外部用户查看任一导出类型、函数或方法时，godoc 应说明用途、关键字段、错误条件、资源释放要求和边界。
- When 维护者审查根包 API 时，公开 DTO、配置、查询 Builder、Engine 方法、降采样 API 应按职责拆分到小文件，避免单文件承载全部语义。
- When 底层 internal model 演进时，根包 DTO 应继续保持外部兼容，不泄漏 internal 类型。

**实施项:**

- 为根包所有导出标识符补 godoc。
- 将 `types.go` 按职责拆分为 `values.go`、`options.go`、`query_types.go`、`result_types.go`、`downsample_types.go`、`engine_types.go`、`convert.go`。
- 保持行为不变，先补测试确保拆分不改变 API。

**验收:**

- `golangci-lint` 启用导出注释检查时根包不报缺失注释。
- 根包单文件行数满足项目约束。
- `go test . -count=1` 通过。

**实现备注:** 已补齐根包 package、核心类型、Builder、Engine、降采样、结果与配置的 godoc；原 `types.go` 已按职责拆分为 `values.go`、`options.go`、`query_types.go`、`result_types.go`、`downsample_types.go`、`engine_types.go` 以及转换文件。根包单文件均保持在项目约束内。

### Task 4：P0 错误契约稳定化

**状态:** 已实施。

**EARS:**

- When 外部用户收到错误时，应能用 `errors.Is` 或稳定错误码区分 invalid input、not found、already exists、budget exceeded、context canceled、storage corrupted、unsupported。
- When 查询 Builder 输入非法时，应返回带上下文的稳定错误，而不是只有笼统 `ErrInvalidQuery`。
- When HTTP 协议未来外放时，Go library 错误与 HTTP error code 应能一一映射。

**实施项:**

- 盘点 internal 到 root 的错误传播。
- 在根包定义稳定 sentinel errors 或 `Error` 类型。
- 保持 `ErrInvalidQuery`、`ErrReadBudgetExceeded` 兼容。
- 给常见错误路径补 `errors.Is` 测试。

**验收:**

- 外部测试覆盖 open invalid path、invalid query、budget exceeded、not found、unsupported。
- 错误消息可读，但测试不依赖不稳定全文。

**实现备注:** 已新增 `ErrInvalidOptions`、`ErrNotFound`、`ErrUnsupported` 与 `publicError` 映射；保留 `ErrInvalidQuery`、`ErrReadBudgetExceeded` 兼容。已覆盖 invalid query、budget exceeded、missing downsample policy、unsupported aggregate 等 `errors.Is` 契约。

### Task 5：P1 Builder 易用性与安全默认

**状态:** 已实施。

**EARS:**

- When 用户按自然 Go 方式构造时间范围查询时，Builder 应支持 `time.Time` 入口，避免用户手写 Unix nano。
- When 用户构造聚合查询时，系统应提供稳定聚合常量或 helper，避免魔法字符串。
- When 用户构造可能 materialize 大结果的查询时，文档和 API 应引导使用 iterator、limit 和 budget。

**实施项:**

- 新增 `TimeRangeTime(start, end time.Time)`。
- 新增聚合函数常量，或新增 `AggregateAvg`、`AggregateMax` 等 helper。
- 在 `QueryRows`、`QueryColumns` godoc 和 README 中明确小结果限制，推荐 iterator。
- 评估是否为 `QueryRows`/`QueryColumns` 增加 opt-in 安全上限；如涉及 breaking change，单独规格确认。

**验收:**

- Builder 示例不再要求外部用户直接写 Unix nano。
- 聚合函数拼写错误在 Build/Analyze 阶段稳定报错。
- 大结果路径有 iterator 示例和预算说明。

**实现备注:** 已新增 `TimeRangeTime` 与聚合常量；README 和 godoc 已明确 `QueryRows`/`QueryColumns` 适合小结果集，大结果应优先使用 iterator、Limit 和 QueryBudget。

### Task 6：P1 写入 API 所有权与批量写入契约

**状态:** 已实施。

**EARS:**

- When 用户调用 `Write` 或 `WriteTypedBatch` 后继续复用输入 slice/map 时，系统应有明确所有权契约，不允许产生隐式数据污染。
- When typed batch 列长度、字段类型或 tag 列长度非法时，系统应返回稳定错误。
- When 用户需要高吞吐写入时，文档应推荐 typed batch 路径，并说明适用场景和限制。

**实施项:**

- 给 `Point`、`TypedBatch`、`Write`、`WriteTypedBatch` 补所有权 godoc。
- 补充输入复用、字段类型错配、空字段、tag 长度错配测试。
- README 增加 typed batch 简例或链接到专门文档。

**验收:**

- 外部用户能明确知道哪些输入会被拷贝、哪些不应并发修改。
- `WriteTypedBatch` 错误路径都有测试。

**实现备注:** 已在写入 DTO 和公开写入方法 godoc 中说明输入所有权；已补充 `Write` 与 `WriteTypedBatch` 输入复用测试，以及 typed batch 长度错误路径测试。README 已加入 typed batch 简例。

### Task 7：P1 降采样 API 易用性与文档闭环

**状态:** 已实施。

**EARS:**

- When 用户创建降采样策略时，系统应提供最小策略示例，说明源/目标 retention、函数、tag、watermark、repair 和 dry-run。
- When 用户查询降采样结果时，Builder 应提供明确入口并自动附带 policy tag。
- When 用户删除或重置策略时，文档应说明是否清理目标 rollup 数据及其风险。

**实施项:**

- 为 `DownsamplePolicy` 及相关方法补 godoc。
- README 保留最小入口，详细说明链接到 `docs/storage/downsample-runbook.md`。
- 新增 `ExampleEngine_CreateDownsamplePolicy` 或更小的可执行示例。

**验收:**

- 降采样 public API 在 pkg.go.dev 可读。
- 示例测试通过。

**实现备注:** 已补齐降采样类型和公开方法 godoc；README 保留最小入口并链接到 `docs/storage/downsample-runbook.md`；根包测试覆盖 create/list/enable/disable/run/range/repair/dry-run/status/reset/drop options 等公开路径。

### Task 8：P1 外部服务 API 边界决策

**状态:** 已实施。

**EARS:**

- When 产品目标包含 HTTP 查询服务时，系统应提供非 internal 的稳定 server package、request/response schema、错误码、streaming 契约和认证边界。
- When 当前版本不承诺 HTTP 外部 API 时，README 应明确仅 Go library 和 `mts-storage` CLI 是当前对外接口。
- When 未来外放 HTTP API 时，internal 协议应先冻结 schema 并补 OpenAPI 或等价机器可读文档。

**实施项:**

- 当前建议先文档化“不外放 HTTP API”，避免用户 import `internal`。
- 若确认需要外放，新增单独规格设计 `mtshttp` 或 `server` package。

**验收:**

- 外部用户不会误以为 `internal/queryservice` 是稳定公共 API。
- README 的对外接口边界清晰。

**实现备注:** README 已明确当前稳定对外接口只有根包 `github.com/openmts/mts` 和 `cmd/mts-storage`；`internal/queryservice`、`internal/service` 不承诺为外部稳定 API。

## 建议实施顺序

1. Task 1：先补 README、doc.go、可执行示例，让 API 可发现。
2. Task 2：补默认配置和配置校验，让最小集成路径变短。
3. Task 3：补 godoc 并拆分根包 API 文件，让外部契约可维护。
4. Task 4：稳定错误契约，让用户能写可靠集成代码。
5. Task 5-7：增强 Builder、写入和降采样易用性。
6. Task 8：明确 HTTP API 是否外放，避免兼容面失控。
7. Task 9-10：补发布交付物和质量门禁证据。

## 当前不建议立即做的事

- 不建议把 `internal/queryservice` 直接搬成公共 API。协议一旦外放，兼容成本会显著增加，应先完成根包商用化。
- 不建议新增 SQL/InfluxQL/PromQL parser。当前项目边界已经明确 Builder/API 是查询入口。
- 不建议在未确认许可证前对外声明“可商用”。没有 LICENSE 时，外部用户无法可靠判断使用权。
- 不建议为了“易用”隐藏 iterator 和 budget。时序查询天然可能返回大量数据，易用性应建立在明确资源边界上。
