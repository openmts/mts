# 存储层代码架构耦合度检视

## 用户问题本质

用户希望确认 mts 存储层是否已经做到足够解耦，后续新增小需求时是否可以通过接口扩展完成，而不是牵动 WAL、MemTable、SSTable、Catalog、Engine 等底层大范围调整。

## 结论

当前存储层的包级拆分基本清晰，没有发现循环依赖。整体依赖方向是 `engine -> catalog/memtable/wal/sstable/storagefs -> model/codec/storagefs`，这对概念设计阶段是可维护的。

但从“后续需求变动成本”角度看，当前仍偏向 concrete-first 架构：`engine.Shard` 直接持有并调用 WAL、MemTable、SSTable、Manifest、文件系统的具体实现。功能已经分包，但 orchestration 层没有端口接口隔离。因此现在的耦合度评价是：包边界中等偏好，核心组装层耦合偏高。

## 发现项

### 建议修改：Shard 直接绑定 WAL/MemTable/SSTable 具体类型

状态：已实施。已在 `internal/engine/ports.go` 定义消费方端口，并将 `Shard` 的 WAL、MemTable、Part 依赖切换为接口字段和默认适配器。

位置：
- `internal/engine/shard.go:30`
- `internal/engine/shard.go:49`
- `internal/engine/shard.go:107`
- `internal/engine/shard.go:147`

现象：

`Shard` 字段直接使用 `*wal.Log`、`*memtable.MemTable`、`[]*sstable.Part`，`OpenShard` 内部直接调用 `memtable.New()`、`wal.Open()`、`sstable.LoadManifest()`，写入和 flush 路径直接调用具体方法。

影响：

如果后续要替换 WAL 策略、增加分层 MemTable、引入新的 Part reader/writer、做故障注入测试或支持不同存储后端，改动会集中冲击 `Shard`。目前测试也通过 `shardTestHooks` 和访问内部结构完成故障模拟，说明接口边界还不够自然。

建议：

在 `internal/engine` 消费方定义小接口，不要在实现包里定义大接口。优先抽出：

- `walAppender`：`Append`、`AppendTombstones`、`ReplayRecords`、`Checkpoint`、`Close`
- `memStore`：`ApplyBatch`、`SampleCount`、`SnapshotAndReset`、`Restore`、`Query`
- `partStore` 或 `partManager`：`LoadManifest`、`OpenPart`、`WritePart`、`NewPartWriter`、`WriteManifest`

不要一次性做大抽象。先从 `partManager` 入手，因为 flush/compaction/manifest 是当前耦合最重的变化点。

### 建议修改：flush 与 compaction 直接操作 SSTable 格式细节

状态：已实施。flush、open parts、manifest 提交、streaming compaction writer、compaction reader 创建和旧 part 删除已通过 `partManager` / `fileOps` 端口调用。

位置：
- `internal/engine/shard.go:160`
- `internal/engine/shard.go:173`
- `internal/engine/shard.go:180`
- `internal/engine/lifecycle.go:83`
- `internal/engine/lifecycle.go:319`
- `internal/engine/lifecycle.go:356`

现象：

flush、compaction 直接使用 `sstable.WritePartWithOptions`、`sstable.OpenPart`、`sstable.WriteManifest`、`sstable.NewPartWriter`。`compactionOutput` 也直接持有 `*sstable.PartWriter` 和 `[]*sstable.Part`。

影响：

如果后续要调整 SSTable 落盘流程，例如增加 staging manifest、两阶段提交、对象存储适配、part 文件布局调整、page writer 策略切换，`engine` 需要同步改动。SSTable 的持久化细节没有被集中封装在一个 storage adapter 后面。

建议：

新增 engine 内部消费接口：

```go
type partManager interface {
    LoadManifest(dir string) (sstable.Manifest, error)
    OpenPart(path string) (partReader, error)
    WritePart(dir string, level int, id string, columns []model.ColumnData, opts sstable.WriteOptions) (sstable.PartMeta, error)
    NewWriter(dir string, level int, id string, opts sstable.WriteOptions) (partWriter, error)
    WriteManifest(dir string, manifest sstable.Manifest) error
}
```

其中 `partReader`、`partWriter` 继续保持 2-4 个方法。默认实现包装现有 `sstable` 函数。这样 SSTable 格式变化优先落在 adapter 内，而不是散落到 Shard。

### 建议修改：public API 与 internal/model 使用 type alias 强绑定

状态：已实施。根包 public 类型已由 type alias 改为独立 DTO，并在 public engine wrapper 边界显式转换为 internal model。

位置：
- `types.go:10`
- `types.go:21`
- `types.go:25`
- `internal/model/types.go:50`
- `internal/model/types.go:127`
- `internal/model/types.go:159`

现象：

根包通过 type alias 暴露 `internal/model` 的类型。`internal/model` 同时包含外部 API 类型、内部解析类型、存储列类型、tombstone、iterator 接口。

影响：

内部字段调整会直接变成外部 API 变化。例如后续为了压缩内存调整 `ColumnData`、`VersionedSample`、`ResolvedPoint`，需要同时考虑 public API 兼容。这个耦合会抬高底层存储结构演进成本。

建议：

逐步拆分模型层：

- `internal/model` 保留内部存储与执行模型，例如 `ResolvedPoint`、`ColumnData`、`VersionedSample`
- 根包保留稳定 API DTO，例如 `Point`、`Query`、`ColumnSeries`、`Row`
- 在 engine 边界做转换，避免 public API 直接 alias 内部结构

当前是概念阶段，尚未承诺兼容性，可以尽早拆，越晚成本越高。

### 建议修改：Query iterator 名义是接口，实际仍一次性物化

状态：已实施。`QueryColumnIterator` 已改为保存 raw `ColumnData` 和 catalog snapshot，并在 `Column()` 时延迟装饰当前列；本轮完成的是 iterator 装饰边界与 internal/public 模型隔离，不改变底层查询执行策略。

位置：
- `internal/engine/query.go:12`
- `internal/engine/query.go:37`
- `internal/engine/query.go:55`
- `internal/engine/query.go:70`

现象：

`QueryColumnIterator` 返回内部 `columnIterator`，但 iterator 内部持有完整 `[]model.ColumnSeries`；`QueryRowIterator` 也是先 `QueryColumns`，再一次性转换成 rows。

影响：

接口形态已经有了，但底层并不是 lazy streaming。后续要支持大查询、分块读取、取消、分页、下推过滤时，仍然会牵动 engine 查询路径和数据结构。

建议：

保留 public iterator API，但内部逐步改为真正的流式 reader：

- Shard 层返回 `ColumnDataIterator`
- MemTable/SSTable 分别实现 reader
- Engine 做 merge/decorate iterator
- Row iterator 基于 column iterator 聚合，而不是先物化所有 columns

这项不建议和当前热路径优化混在一起做，应该作为查询层架构专项。

### 仅供参考：storagefs 是函数集合，不利于文件系统故障注入

状态：已实施最小端口。Shard 相关删除路径已通过 `fileOps` 注入；`storagefs` 包本身保持函数集合，避免在当前阶段过度抽象文件系统。

位置：
- `internal/storagefs/fs.go:13`
- `internal/storagefs/fs.go:21`
- `internal/storagefs/fs.go:48`
- `internal/storagefs/fs.go:59`

现象：

`storagefs` 以包函数方式提供 `MkdirAll`、`WriteFileAtomic`、`SyncDir`、`RemoveAll`。调用方直接引用函数。

影响：

当前实现简单可靠，但对故障注入、内存 FS、对象存储、限速 FS 等场景不够友好。很多错误路径测试只能依赖非法路径、权限或包内 hook。

建议：

短期不需要全量抽象文件系统。更实际的方式是在 `engine` 和 `sstable` 的存储 adapter 里引入最小 `fileOps` 接口，只覆盖需要故障注入的 3-5 个操作。

## 当前做得好的地方

- 包级依赖没有循环，`engine` 是明确的组装层。
- WAL、MemTable、SSTable、Catalog 已经分别有独立包和独立测试。
- `storagefs` 统一了目录和文件权限，降低安全策略散落风险。
- `model.FieldType` 从 1 开始，避免零值误认为合法类型。
- 当前接口没有泛滥，符合 Go 的“先具体实现，再从消费方抽接口”的原则。

## 建议的演进顺序

1. 先抽 `partManager`，把 flush、compaction、manifest、part open/write 从 Shard 中隔离出来。
2. 再抽 `walAppender` 和 `memStore`，让 Shard 构造可以注入依赖，替代测试 hook。
3. 拆分 public API DTO 与 internal storage model，停止根包 type alias 内部类型。
4. 最后做真正流式 query iterator，把现在的物化 iterator 改为分层 reader。

## 风险评估

不建议为了“接口化”一次性把所有包都改成接口。Go 里过早抽象会增加调用链和测试复杂度。当前真正需要接口隔离的是 engine 消费方，尤其是 Shard 依赖的 WAL/MemTable/SSTable/Manifest。其他包内部的具体函数可以保留，等出现第二实现或明确测试需求再抽。
