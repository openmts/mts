# 存储层完整性检视报告

## 问题本质

用户希望判断当前 mts 存储层是否已经足够完整，是否可以在此基础上继续构建现代化时序数据库的上层能力。

## 检视结论

当前存储层已经具备“单机嵌入式时序存储内核”的主干能力，可以作为后续元数据管理、Engine 服务层、写入协议、查询接口和运维工具的基础继续建设。

但如果以“现代化时序数据库产品”的完整标准衡量，它还不是最终形态。缺口主要不在 WAL/MemTable/SSTable/Compaction 的主链路，而在查询执行器能力、生产级调度与观测、长期性能基准、schema/metadata 治理、服务化接口和多租户/集群能力。

## 已具备能力

- WAL：二进制 WAL、批量写入、强同步、批量 fsync、segment、replay、尾部半条截断、中间损坏报错。
- MemTable：列式 typed buffer、LWW、snapshot、flush 失败恢复、写入路径内存优化。
- SSTable：目录式列式 Part、二进制 manifest/metadata/index、metaindex 粗筛、field/time/series 裁剪、CRC/envelope 校验。
- 压缩：支持 typed encoding，并支持 snappy、lz4、zstd payload compression。
- Compaction：支持 streaming compaction、bounded cascade level compaction、逐层阈值、逐层输出大小、逐层压缩配置。
- Recovery：支持 manifest 加载、WAL replay、flush manifest recovery、孤儿 Part 清理。
- Retention/Sharding：支持时间 shard、跨 shard 查询、retention 以 shard 为边界清理。
- 接口隔离：engine 侧已通过 WAL/MemTable/Part/文件操作端口降低直接耦合。
- 测试：单元测试、e2e、pprof workload 已覆盖主要功能路径。

## 不应视为已完成的产品级能力

### 查询执行器仍偏基础

当前 `QueryRows` / `QueryColumns` 已可用，Part 级和 block/page 级裁剪也已经具备，但查询执行器还不是完整现代 TSDB 查询层。缺少真正面向大结果集的跨 shard streaming executor、分页/取消下推、聚合/窗口函数、表达式执行和 cost-based 选择。

影响：可以继续构建上层读写 API，但不应直接承诺复杂查询性能已经达到成熟 TSDB 水平。

### Compaction 是可用的 leveled 策略，不是严格 RocksDB 式 non-overlap leveled

当前实现符合“本层合并，达到阈值晋升下一层”的目标，且保留 streaming 执行。但 L1+ 尚未强约束同层 key/time range 完全不重叠，也没有并发 compaction 的文件占用调度。

影响：读放大会显著收敛，但还不是理论最优的严格 leveled layout。

### 生产级后台调度与观测还需要上层化

已有 background compaction interval 和 pprof 工具，但还缺少指标体系、compaction backlog/score、WAL/flush/compaction 队列观测、慢查询统计、错误注入和可运维配置热更新。

影响：嵌入式内核可用，服务化运行还需要 observability 和调度控制。

### 长周期压力与故障矩阵仍需要扩大

当前 `go test ./...` 和 e2e 通过，之前也跑过 100K/1M pprof 场景。但现代 TSDB 需要长期 soak、异常掉电矩阵、磁盘满、fsync 失败、并发 query/write/compact、retention 与 compaction 交错等测试。

影响：功能正确性基础成立，生产可靠性还要继续用更强测试证明。

## 本次新鲜验证

- `go test -count=1 ./... -timeout 600s`：通过。
- `tests/e2e/*` 逐个 `go build -o testbin . && timeout 120s ./testbin`：全部通过。
- e2e 临时二进制已清理。

## 能否继续构建现代化时序数据库

可以继续构建，但建议把当前存储层定义为“可演进的单机存储内核 v1”，而不是“产品级 TSDB 完整存储层终局”。

下一阶段最合理的方向是：

1. 在当前存储层之上建设清晰的 engine service 层，把 database、measurement、retention policy、schema、shard lifecycle 和读写 API 统一起来。
2. 建设查询执行层，先支持流式 scan、聚合、分页、取消和跨 shard merge。
3. 建设生产级观测与调度，包括 metrics、pprof endpoint、compaction score、flush backlog、WAL backlog、错误计数。
4. 建设长期性能与故障测试矩阵，把 1M/10M 写入、重启恢复、compaction backlog、RSS/CPU 上限纳入稳定 benchmark gate。

## 最终判断

从“继续上层开发”的角度：可以。

从“对标 InfluxDB/Prometheus/VictoriaMetrics 的成熟产品存储层”的角度：还需要查询执行器、严格读放大控制、后台调度、观测、故障矩阵和长期压测继续补齐。
