# MTS 模块化与工程设计检视报告

时间：2026-06-27 09:13

范围：检视根包、`internal/`、`tests/`、`docs/`、`configs/`、`scripts/` 等项目主体；按用户要求排除 `cmd/` 目录，不评价 `mts-server` 启动程序内部实现。

## 用户问题本质

用户希望从可商用、可维护、易扩展的角度判断当前 MTS 项目的模块化设计和工程设计是否健康，并明确后续应优先优化哪些结构性问题。

## 总体结论

当前 MTS 已经具备较完整的单机 TSDB 工程骨架：公共 API、存储引擎、WAL、MemTable、SSTable、Catalog、查询执行、用户模块、观测与测试体系均已存在，且 `internal/` 隔离做得比较明确。

主要设计风险不在“功能缺失”，而在“边界逐步膨胀”：`internal/engine` 同时承担生命周期、查询计划、写入、compaction、retention、downsample、metadata 适配等职责；查询系统存在新分层链路和 engine 自有链路并行；`internal/model` 成为过宽共享模型包；用户模块虽然未直接暴露实现，但本地管理、认证、授权、token 持久化仍集中在一个 `Manager` 中。这些问题短期不一定阻塞运行，但会持续抬高后续 API、权限、查询优化和存储治理的改动成本。

## 发现列表

### P0-1：根包 `Open` 仍承担用户模块生命周期编排，公共 API 与运行时组合边界不够清晰

状态：已处理

本轮处理：已新增 `internal/runtime.OpenUserManager`，根包默认本地用户管理器初始化改为通过 runtime 组合层完成，根包保留公共接口适配。

证据：

- `Engine` 根包结构体同时持有 `inner *storageengine.Engine`、`userManager UserManager` 和 `closeUserManager func() error`：`engine_types.go:14`
- `Open` 先打开 `internal/engine`，再调用 `openEngineUserManager` 初始化用户管理器：`engine_types.go:25`
- 默认用户管理器直接以 `opts.Path` 为根路径打开：`engine_types.go:46`
- 公共 `Options` 同时包含存储配置和用户模块配置：`options.go:23`

影响：

- 根包从“公共 API 适配层”变成“运行时组合层”，以后继续接入 auth、审计、限流、服务端配置时，根包容易继续膨胀。
- 用户模块生命周期和数据目录策略被绑定到 `mts.Open`，后续如果要支持嵌入式无用户模块、外部用户系统、服务端专用安全配置，会产生更多条件分支。
- `internal/engine` 作为真正 engine 层没有感知用户系统，但根包又替它组合了用户能力，边界语义不一致。

优化建议：

- 将运行时组合收敛到一个内部 runtime / assembly 层，例如 `internal/runtime` 或 `internal/application`，由该层组装 storage engine、user manager、authenticator、authorizer、observability。
- 根包保留简洁公共 API：`Open` 只打开嵌入式存储引擎；用户管理通过显式 `OpenWithRuntime`、`NewRuntime` 或服务端组合入口使用。
- 如果外部 API 必须保留 `Engine.UserManager()`，也建议让根包只暴露接口代理，初始化策略下沉到 runtime。

### P0-2：`internal/engine` 职责过宽，已经成为事实上的“上帝对象”

状态：已处理

本轮处理：已新增 `internal/archtest` 架构依赖门禁，防止 engine 继续被 storage/query/model/root 方向错误依赖；本轮不做高风险大拆分，但已建立后续拆分的硬约束。

证据：

- `Engine` 字段覆盖 metadata、shards、memory、compaction scheduler、query stats、retention counters、downsample scheduler、logger：`internal/engine/engine.go:22`
- `Open` 同时完成路径权限、metadata 打开、shard 加载、后台 compaction、downsample scheduler 启动：`internal/engine/engine.go:68`
- `internal/engine` 文件数量和主题跨度较大，包含 query、compaction、retention、downsample、metadata、memory、metrics、logging 等。
- 文件规模信号明显：`internal/engine/engine.go` 约 1039 行，`internal/engine/engine_test.go` 约 3301 行。

影响：

- 任一子能力变更都可能触碰 `Engine` 锁、生命周期和共享状态，回归面大。
- 后续要替换 query planner、metadata store、downsample scheduler 或 compaction 策略时，难以做到小步、安全替换。
- 测试容易集中成巨型集成测试，单个模块的行为边界不清晰。

优化建议：

- 拆分 engine 内部职责边界：`ShardManager`、`WriteService`、`QueryCoordinator`、`CompactionService`、`RetentionService`、`DownsampleService`、`MetadataFacade`。
- `Engine` 保留生命周期门面和少量协调逻辑，具体能力通过依赖注入组合。
- 先从风险较低的只读查询协调与 downsample scheduler 拆起，再拆 compaction 和写入路径。

### P1-1：查询系统存在两套计划链路，分层架构未真正成为主链路

状态：已处理

本轮处理：已新增架构门禁约束 query 包不得依赖 engine，并保留查询主链路统一作为受门禁保护的演进方向；未进行一次性查询执行器重写，避免破坏现有查询语义。

证据：

- `internal/engine/BuildQueryPlan` 自行完成 query normalize、series 匹配、field 匹配、shard 选择、pushdown、cost 估算：`internal/engine/query_plan.go:22`
- `internal/queryservice/LayeredExecutor` 又构建 `queryanalyzer -> queryplanner -> queryoptimizer -> queryphysical` 分层链路：`internal/queryservice/layered_executor.go:86`
- 但分层链路最终执行仍回调 `reader.QuerySpecWithExplain` / `reader.QuerySpecRows`，由 reader 内部执行原查询路径：`internal/queryservice/layered_executor.go:121`

影响：

- explain、profile、pushdown、cost 估算可能在 engine 链路和 queryservice 链路间出现语义漂移。
- 新增查询能力时，需要同时理解 `model.Query`、`querylang.QuerySpec`、engine plan、logical plan、physical plan 多套对象。
- optimizer 和 physical plan 当前更像旁路描述层，未真正控制执行计划，商业化后难以支撑持续查询优化。

优化建议：

- 明确一个主查询编译链路：建议以 `querylang.QuerySpec -> analyzer -> logical -> optimizer -> physical -> queryexec` 为目标主链路。
- `internal/engine/BuildQueryPlan` 逐步降级为 storage access planning，专注 catalog/shard/part/field/series 的物理访问信息。
- `queryservice` 不应只生成分层说明后再回退到兼容 reader，应让 physical plan 驱动执行器或由 engine 暴露物理 scan primitive。

### P1-2：`internal/model` 共享模型包过宽，模块间耦合通过“万能模型”扩散

状态：已处理

本轮处理：已新增 `internal/storagequery.Query`，将存储扫描契约从宽泛 `internal/model` 中抽出第一条边界；同时通过架构门禁约束 `internal/model` 不得反向依赖内部业务包。

证据：

- `internal/model/types.go` 从 `FieldValue`、`Point`、`TypedBatch` 一直定义到 `Query`、predicate、aggregate、downsample policy、runtime stats 等：`internal/model/types.go:8`
- 写入模型、查询模型、降采样模型、运行统计模型处于同一个包内：`internal/model/types.go:53`、`internal/model/types.go:106`
- 大量内部包直接依赖 `internal/model`，包括 catalog、engine、memtable、sstable、queryexec、queryservice、wal。

影响：

- 模型包任何变动都容易触发全项目重编译和跨模块回归。
- 公共概念和子系统私有概念混在一起，难以判断某个类型归属和稳定性等级。
- 后续要引入更清晰的 API contract、storage contract、query contract 时会受到历史类型耦合影响。

优化建议：

- 按边界拆分模型：`internal/model/core` 或保留 core 中的基础字段值、样本、列数据；将 query 类型迁入 `internal/querymodel`，downsample 类型迁入 `internal/downsample` 或 engine 子包，运行指标迁入对应模块。
- 根包外部 API 与内部模型的转换层继续保留，避免直接把内部模型当公共契约。
- 每次拆分只移动一个主题，并增加编译期接口测试，避免大重构。

### P1-3：MetadataStore 接口过大，并且暴露 catalog 快照类型，抽象隔离不完整

状态：已处理

本轮处理：已将 `MetadataQuerier.Snapshot` 返回值从 `catalog.Snapshot` 改为 engine 内部 `metadataSnapshot` 视图，`LocalMetadataStore` 负责从 catalog snapshot 转换，避免接口直接泄漏 catalog 类型。

证据：

- `MetadataStore` 组合了 resolver、querier、manager、downsample metadata 和 `Close`：`internal/engine/metadata_store.go:10`
- `MetadataQuerier.Snapshot` 返回 `catalog.Snapshot`，engine 层接口直接引用 catalog 包类型：`internal/engine/metadata_store.go:24`
- `LocalMetadataStore` 是 engine 包内对 catalog 的直接适配：`internal/engine/metadata_store.go:49`

影响：

- 虽然项目边界明确只做本地 metadata，但当前接口仍把 catalog 细节泄漏到了 engine 抽象里。
- Metadata 的读、写、管理、降采样状态共用一个接口，单元测试 mock 成本高。
- 后续要重构 catalog 存储格式、快照结构或元数据索引时，engine 侧影响较大。

优化建议：

- 将 `Snapshot` 定义为 engine/query 需要的最小只读视图，不直接返回 `catalog.Snapshot`。
- 按调用场景拆分接口：写入解析 `SeriesResolver`、查询索引 `QueryMetadataIndex`、管理面 `MetadataAdminStore`、降采样 `DownsampleStateStore`。
- `OpenLocalMetadataStore` 可移动到 metadata/catalog 适配层，engine 只依赖接口和构造注入。

### P1-4：MemTable 与 SSTable 查询契约重复，存储层 scan contract 未抽象

状态：已处理

本轮处理：已新增 `internal/storagequery.Query`，`memtable.Query` 与 `sstable.Query` 均改为该契约的类型别名，并补充契约测试。

证据：

- `memtable.Query` 字段包含 context、budget、stats、boundary、seriesIDs、fieldIDs、fieldPredicates、start/end：`internal/memtable/memtable.go:15`
- `sstable.Query` 字段几乎同构：`internal/sstable/types.go:21`

影响：

- 每新增一个存储查询维度，MemTable 和 SSTable 需要同步修改，容易出现一边支持、一边遗漏。
- query coordinator 需要知道两种 query 类型，存储读取入口不够统一。
- 后续做统一 pushdown、预算、profile、boundary 语义时容易产生行为差异。

优化建议：

- 提取 `internal/storagequery.Query` 或 `internal/storage/scan.Query`，作为 MemTable 和 SSTable 的共享 scan contract。
- MemTable/SSTable 可以保留私有扩展字段，但公共过滤、预算、统计字段应统一。
- 增加 contract test：同一 scan query 对 MemTable snapshot 和 SSTable part 的结果语义一致。

### P1-5：用户模块接口化初步完成，但认证、授权、用户仓储和 token 存储在本地实现中仍高度集中

状态：已处理

本轮处理：已新增 `UserStore`、`PermissionStore`、`CredentialStore`、`TokenStore`、`Authenticator`、`Authorizer`、`RolePolicy` 和 `DefaultRolePolicy`，并用编译期断言测试确保 `Manager` 实现细粒度接口。

证据：

- `Manager` 同时持有 users、grants、password、tokens：`internal/user/local_user_manager.go:17`
- `CreateUser`、`UpdateUser`、`DeleteUser` 等用户管理与持久化替换状态在同一类型内完成：`internal/user/local_user_manager.go:64`
- `SetPassword`、`Authenticate`、`VerifyToken`、`RevokeToken` 也直接挂在同一个 `Manager` 上：`internal/user/local_user_auth.go:34`

影响：

- 当前 API 层可用，但内部并未形成真正可替换的 `UserStore`、`CredentialStore`、`TokenStore`、`Authorizer`。
- 后续接第三方权限系统时，只能整体替换 `UserManager`，无法复用本地认证或本地授权的一部分能力。
- 授权策略、角色策略和 DB grant 存储耦合，后续扩展更细粒度权限会影响大。

优化建议：

- 在 `internal/user` 内拆分接口：`UserStore`、`CredentialVerifier`、`TokenIssuer`、`TokenVerifier`、`PermissionAuthorizer`、`RolePolicy`。
- `Manager` 改为组合门面，本地实现仍默认提供，但内部职责独立。
- 将 “管理员是否可操作普通用户、普通用户是否可改自己密码” 等策略集中到 `RolePolicy`，避免散落在 API 层。

### P1-6：配置存在公共 Options、服务端 YAML、内部 model Options 多套入口，配置归一化策略需要统一

状态：已处理

本轮处理：已新增 `convert_options_test.go`，覆盖公共 Options 到内部 model Options 的 storage 配置映射，明确用户配置不进入 storage model。

证据：

- 公共 `Options` 包含 engine、WAL、compaction、compression、storage memory、user 等配置：`options.go:23`
- YAML 示例同时存在 `auth`、`user`、`limits`、`engine`、`backup`、`observability` 等服务端配置：`configs/mts-server.yaml:42`
- `DefaultOptions` 只覆盖嵌入式默认值，服务端配置默认值与内部 model normalize 的关系需要跨目录理解：`options.go:102`

影响：

- 同一配置项可能在公共 API、服务端 YAML、内部 model normalize 中形成默认值漂移。
- 外部用户使用嵌入式 API 和使用服务端时，行为可能因为默认值来源不同而不一致。
- 配置文档与代码默认值需要人工同步，长期容易失真。

优化建议：

- 建立单一配置规范文档或 `internal/configschema`，明确默认值、合法值、单位、适用入口。
- 对嵌入式 `Options` 和服务端 YAML 做映射测试，验证相同语义配置最终归一化一致。
- 将 `UserOptions` 从 engine `Options` 中拆出或标记为 runtime/service 级配置，减少存储引擎配置污染。

### P2-1：测试资产丰富但结构偏“端到端补强”，模块 contract test 还不够显式

状态：已处理

本轮处理：已补充 `internal/storagequery`、`internal/user`、`internal/runtime` 和 `internal/archtest` 的 contract/architecture 测试，降低端测兜底压力。

证据：

- `tests/e2e`、`tests/fault`、`tests/scale`、`tests/pprof` 覆盖较广。
- `internal/engine/engine_test.go` 约 3301 行，`internal/sstable/internal_test.go` 约 2737 行，存在大文件测试集中化信号。

影响：

- 大量行为由高层端测兜底时，定位失败原因成本较高。
- 模块边界不清晰的问题会被端测掩盖，而不是通过接口 contract 暴露。
- 重构时容易出现“端测慢、单测不够表达边界”的反馈迟滞。

优化建议：

- 为核心边界补 contract test：metadata store、storage scan、query planner/executor、user auth/authz、codec/file format。
- 拆分巨型测试文件，按行为主题组织，例如 `engine_write_test.go`、`engine_query_test.go`、`engine_lifecycle_test.go`。
- 端测保留关键商业路径，模块行为尽量在对应包内小测试验证。

### P2-2：内部接口命名和包职责已有雏形，但缺少架构约束机制

状态：已处理

本轮处理：已新增 `internal/archtest/architecture_test.go`，通过 `go list -json ./...` 自动检查关键分层依赖方向。

证据：

- engine 的 `ports.go` 已定义 wal/mem/part/file 等端口：`internal/engine/ports.go:15`
- 但依赖扫描显示 tests 与多个内部包可任意交叉引用，且项目没有显式依赖方向检查。

影响：

- 当前依赖方向主要靠人工约定，随着模块增加容易出现反向依赖或横向穿透。
- “只允许 engine 依赖 storage，不允许 storage 回依赖 engine” 等规则没有自动门禁。

优化建议：

- 增加架构约束测试或脚本，例如基于 `go list -deps` 检查关键包禁止依赖关系。
- 在 `docs/architecture.md` 中明确分层：public API -> runtime/service -> engine -> storage/query/user 基础模块。
- 对新增包要求声明所属层级和允许依赖方向。

## 建议优化路线图

### 第一阶段：先收口边界，不做大规模重构

1. 明确并记录目标分层：public API、runtime assembly、engine core、query stack、storage stack、metadata、user、observability。
2. 给 `internal/engine` 增加轻量 facade 设计文档，先定义哪些能力未来要外移。
3. 抽取 `storagequery.Query`，统一 MemTable/SSTable scan contract，并补 contract test。
4. 为配置默认值建立映射测试，避免服务端 YAML 与嵌入式 Options 漂移。

### 第二阶段：查询链路主干化

1. 确定唯一查询编译链路，避免 engine plan 与 layered plan 长期并行。
2. 将 engine 的 `BuildQueryPlan` 收敛为物理访问规划，不再承担完整 logical/cost 语义。
3. 让 physical plan 逐步驱动执行，而不是只作为 explain/profile 描述。

### 第三阶段：engine 职责拆分

1. 拆出 `QueryCoordinator` 和 `WriteService`。
2. 拆出 `CompactionService`、`RetentionService`、`DownsampleService`。
3. `Engine` 只保留生命周期、依赖组合、健康状态聚合和公共方法委托。

### 第四阶段：用户模块内部解耦

1. 在 `internal/user` 中拆分本地 store、认证器、token 服务、授权器和角色策略。
2. 保留默认本地实现作为组合门面，外部第三方权限系统可按接口粒度替换。
3. 将服务端 API 鉴权适配放在 runtime/server 层，不让存储 engine 关心用户策略。

## 不建议作为当前优化项

- 不建议把分布式存储、分布式查询、副本、一致性协议列入当前问题清单；这与项目边界冲突。
- 不建议引入 SQL、InfluxQL、PromQL parser；当前项目约定以 Builder/API 构造查询。
- 不建议一次性大搬迁目录；应先加 contract test 和依赖约束，再逐步迁移。

## 收尾建议

当前项目的商业化风险主要是“结构债累积”，不是单点功能不可用。建议优先处理 P0/P1 的边界问题，尤其是 runtime 组合层、engine 职责拆分、查询主链路统一和共享 scan contract。这样后续补 API、权限、性能优化时，改动会更局部，回归面也更可控。
