# 降采样功能商用就绪度检视

## 结论

当前降采样功能已经具备单机首版核心链路：可以创建本地 policy，按固定窗口从源 retention policy 聚合数据，并将结果物化写入目标 retention policy；也具备 watermark、本地二进制 metadata、scheduler、metrics、health、e2e/fault/scale smoke 覆盖。

但当前实现还不能判定为商用闭环。它更接近单机 alpha/beta 级能力，适合继续做功能验证和小规模场景试用。与商用时序数据库的降采样能力相比，主要差距集中在调度可取消性、增量进度、一致性治理、流式执行、故障矩阵、运维控制面和规模压测。

## 已完成能力

- Policy 模型与校验已实现，支持 `avg/min/max/sum/count/first/last`，并将 `mean` 归一化为 `avg`：`internal/engine/downsample_validate.go:11`。
- Public API 已暴露创建、启停、删除、列表和手动运行入口：`downsample.go:11`。
- LocalMetadataStore 已接口化接入，policy 和 watermark 通过 catalog 本地二进制文件持久化：`internal/engine/metadata_store.go:40`，`internal/catalog/downsample.go:63`。
- Executor 可以按窗口构造聚合查询并写入目标 retention policy：`internal/engine/downsample_executor.go:65`。
- Scheduler 会随 Engine 启动，按 `RefreshInterval` 扫描 enabled policy，且同一个 policy 同时只允许一个运行实例：`internal/engine/downsample_scheduler.go:12`。
- Watermark 支持成功推进、失败不推进，lookback 可回刷迟到数据窗口：`internal/engine/downsample_executor.go:123`。
- Metrics 和 Health 已接入全局运行统计：`internal/engine/metrics.go:122`，`internal/engine/engine.go:759`。
- 已有 e2e、fault、scale smoke 用例，覆盖基本正确性、目标写失败后 watermark 保留和 100K 级性能报告：`tests/e2e/downsample_policy/main.go:55`，`tests/fault/downsample_policy/main.go:54`，`tests/scale/downsample_policy/main.go:18`。

## 必须修复项

### P0: Scheduler 无法取消运行中的长任务

`scanDownsamplePolicies`、`shouldRunDownsamplePolicy` 和 `startDownsamplePolicyRun` 都使用 `context.Background()`，`stopDownsampleScheduler()` 只关闭 stop channel 并等待 WaitGroup：`internal/engine/downsample_scheduler.go:18`，`internal/engine/downsample_scheduler.go:41`，`internal/engine/downsample_scheduler.go:76`。

影响：

- Engine 关闭时无法主动取消已经进入查询或写入的降采样任务。
- 大窗口、高基数或底层 IO 卡住时，关闭可能长时间阻塞。
- 与设计文档中“关闭时等待运行中任务退出或响应 context cancellation”的 EARS 不一致：`docs/superpowers/specs/2026-06-20-downsample-policy-design.md:179`。

建议：

- Engine 持有 scheduler root context 和 cancel。
- 每次 policy run 派生带超时或可配置 deadline 的 context。
- Close 时先 cancel，再等待任务退出，并把超时/取消状态写入 per-policy status。

### P0: Executor 不是流式降采样，存在高内存风险

`runDownsampleWindow` 对每个窗口调用 `QueryColumns`，拿到完整 `[]model.ColumnSeries` 后再转换为 `[]model.Point`：`internal/engine/downsample_executor.go:77`，`internal/engine/downsample_executor.go:82`。

影响：

- 大窗口、高基数、多字段聚合时，查询结果会在内存中 materialize。
- `downsampleColumnsToPoints` 还会建立 `map[string]*model.Point`、排序 key 和完整 points slice：`internal/engine/downsample_executor.go:259`，`internal/engine/downsample_executor.go:348`。
- 这不符合商用场景对后台任务低内存、可控背压的要求。

建议：

- 降采样执行器应接入流式查询游标或专用聚合流。
- 按 series/group/window 增量输出目标点，分批写入。
- 引入每次 run 的内存预算、输出 batch size 和 backpressure。

### P0: Watermark 只在整批窗口结束后更新，失败会重复大量已成功窗口

`runDownsampleWindows` 在循环内只累加 `maxCompleted`，最后统一写 watermark：`internal/engine/downsample_executor.go:130` 到 `internal/engine/downsample_executor.go:149`。中途失败时，`recordDownsampleRunFailure` 会保留旧 watermark：`internal/engine/downsample_executor.go:152`。

影响：

- 如果一批窗口有 1000 个，第 999 个失败，前 998 个下次仍会重跑。
- lookback 回刷场景可接受重复写，但新窗口批量推进缺少 partial progress，导致写放大和长任务恢复成本过高。
- 无法区分“已成功新窗口”和“回刷窗口”。

建议：

- 拆分 progress：新窗口连续成功后可批量或周期性 checkpoint。
- lookback refresh 不应倒退主 watermark。
- 记录 run-level checkpoint、current window、failed window，支持恢复续跑。

### P0: 首次执行范围与设计不一致，可能漏历史数据

设计要求首次没有 watermark 时应“从源数据查询范围的最早完整窗口开始；若无法推导起点，则从 `now-delay-lookback` 开始”：`docs/superpowers/specs/2026-06-20-downsample-policy-design.md:87`。

当前 `downsampleRunStart` 在 watermark 为 0 时，如果配置 lookback，则直接从 `eligibleUntil-lookback` 开始；如果没有 lookback，只处理最后一个 interval：`internal/engine/downsample_executor.go:201` 到 `internal/engine/downsample_executor.go:219`。

影响：

- 新建 policy 时，如果源数据已存在较长历史，默认不会回填全部历史。
- 用户可能以为创建 policy 后会生成完整历史 rollup，实际只会覆盖 lookback 或最后一个窗口。

建议：

- 明确区分 initial backfill 与 regular refresh。
- policy 支持 `InitialStartTime` 或单独的 backfill API。
- 首次执行可通过源 shard/part 元数据推导最早时间，不能推导时再使用 lookback fallback。

### P0: 设计要求的目标 policy tag 未实现

设计文档要求目标 tags 为 group result tags，并额外写入 `mts_downsample_policy=<name>`：`docs/superpowers/specs/2026-06-20-downsample-policy-design.md:140`。

当前 `downsamplePointForColumn` 只复制 group tags，没有写入 policy tag：`internal/engine/downsample_executor.go:303` 到 `internal/engine/downsample_executor.go:309`。e2e 还明确断言只有 `host` 一个 tag：`tests/e2e/downsample_policy/main.go:141`。

影响：

- 多个 policy 写同一 target measurement 时，无法用 tag 区分来源。
- policy 重命名、函数调整、临时回填任务共用 target 时存在污染风险。

建议：

- 要么实现 `mts_downsample_policy` 保留 tag，并同步更新测试。
- 要么修改设计文档，明确不写该 tag，并要求 target measurement/policy 名称承担隔离责任。

### P1: Policy 变更缺少一致性策略

`CreateDownsamplePolicy` 最终走 `UpsertDownsamplePolicy` 覆盖保存：`internal/engine/downsample_metadata.go:10`，`internal/catalog/downsample.go:23`。

影响：

- 同名 policy 改函数集合、输出字段、group tag 或 target 后，旧目标数据不会清理。
- watermark 是否保留没有语义约束，可能跳过新配置需要重新计算的历史窗口。
- 目标 RP 会混合旧 schema 和新 schema，查询结果不易解释。

建议：

- 对同名 policy 变更做兼容性判断。
- 非兼容变更要求新 policy 名或显式 reset/rebuild。
- 增加 policy revision/hash，watermark 绑定 revision。

### P1: 调度可观测性不足

目前 metrics 只有全局累计和最后一次运行数据：`internal/engine/downsample_stats.go:21`，`internal/engine/metrics.go:122`。

影响：

- 无法知道每个 policy 的 lag、last success、last error、next run、当前窗口、运行耗时分布。
- 多 policy 场景下，单个 policy 持续失败会被全局 `LastPolicy/LastError` 覆盖。
- 难以告警和定位后台任务积压。

建议：

- 提供 per-policy status API。
- metrics 至少包含 policy 维度的 lag、duration histogram、failures、active、last success/error。
- Health 应能报告失败 policy 列表和最严重原因。

### P1: Fault 矩阵不足

现有 fault 用例主要覆盖目标写失败：`tests/fault/downsample_policy/main.go:54`。

缺口：

- query 失败。
- metadata 保存失败。
- metadata 文件损坏后的启动行为。
- 运行中崩溃和重启恢复。
- 磁盘满、fsync 失败、rename 失败。
- scheduler 关闭期间取消和幂等重跑。

影响：

- 无法证明 watermark 和目标数据在异常矩阵下保持一致。
- 难以支撑“功能正确可用”的商用声明。

## 建议增强项

### P1: 缺少 backfill/repair 运维控制面

当前手动入口只有 `RunDownsamplePolicy(ctx, name, now)`：`downsample.go:35`。

建议补齐：

- 指定 `[start,end)` 范围的 backfill。
- repair 某段窗口。
- dry-run 估算窗口数、源样本数、目标点数。
- pause/resume。
- reset watermark。
- 清理某 policy 的目标 rollup 数据。

### P1: 缺少生产级规模压测

`tests/scale/downsample_policy` 默认 `100000` 点、`100` series：`tests/scale/downsample_policy/main.go:18`。

建议补齐：

- 1M/10M raw points。
- 高基数 series。
- 多字段、多函数、多 policy 并发。
- 后台 scheduler 长时间持续运行。
- 降采样任务与正常写入、compaction、查询并发。
- RSS、CPU、GC、磁盘放大和目标点正确性报告落盘。

### P2: 自动查询路由明确不在当前范围，但商用体验仍不足

设计文档明确第一阶段不实现自动查询路由：`docs/superpowers/specs/2026-06-20-downsample-policy-design.md:33`。

影响：

- 用户必须显式查询目标 retention policy。
- 不能根据查询时间范围和精度自动选择 raw/rollup。

建议：

- 当前可以保持不做 SQL/parser，但 Builder 层可以增加显式 rollup policy 选择或推荐 API。

### P2: 不支持 compaction rollup/page-level stats

设计文档明确不在 compaction 阶段生成 rollup SSTable，也不做 page-level 预聚合 stats：`docs/superpowers/specs/2026-06-20-downsample-policy-design.md:37`。

影响：

- 降采样依赖普通查询链路重扫源数据。
- 对超大窗口和超长历史 backfill，效率不如存储层内建 rollup 或 page stats。

建议：

- 保持当前 policy 物化方案作为主链路。
- 后续可以引入只读 page stats 加速 `min/max/count/sum`，但必须先保证一致性和 late data 语义。

## 后续 EARS 清单

- When Engine 关闭时，系统应取消 scheduler root context，并让所有运行中的 downsample query/write 在可配置超时内退出。
- When downsample run 处理新窗口时，系统应按可配置 checkpoint interval 推进连续成功窗口的 watermark，避免中途失败后重跑全部成功窗口。
- When policy 首次运行且用户要求历史回填时，系统应从指定 start 或源数据最早完整窗口开始执行，而不是仅从 lookback 开始。
- When 同名 policy 的函数、group tag、target 或 interval 发生非兼容变更时，系统应拒绝覆盖或要求显式 reset/rebuild。
- When executor 处理大窗口或高基数数据时，系统应使用流式聚合输出和分批写入，避免 materialize 全窗口结果。
- When 多个 policy 并发运行时，系统应提供 per-policy status、lag、last error、next run、duration 和 active 状态。
- When query/write/metadata/fsync/rename/磁盘满/进程重启等异常发生时，系统应保证 watermark 不越过未完成窗口，并通过 fault 用例验证恢复后结果一致。
- When 用户需要补齐历史或修复某段 rollup 时，系统应提供 backfill/repair/dry-run/reset 等显式运维 API。
- When scale workload 运行时，系统应输出 1M/10M、多 policy、高基数、并发写入查询场景下的时间、RSS、CPU、GC、磁盘占用和正确性报告。

## 最终评估

当前降采样功能不适合直接标记为商用完成。它已经完成了规则物化降采样的基本骨架，但离可商用还需要补齐 P0 和 P1 项，尤其是可取消调度、流式执行、历史回填语义、policy 变更一致性、异常矩阵和 per-policy 可观测性。
