# MTS 商用成熟度检视报告

## 结论

当前 MTS 还没有达到“可商用数据库产品”的程度。更准确的定位是：存储内核已经具备研发级工程原型后期能力，核心链路不再是玩具实现，但距离可对外承诺 SLA、可长期无人值守运行、可承受故障矩阵和生产运维要求仍有差距。

项目自身的商用化六大专项文档也明确写明：当前存储层“适合作为研发内核继续演进”，但距离商用级还需要系统补齐可靠性、内存治理、Compaction 长稳、查询执行、文件格式治理和生产运维能力。

## 当前已具备能力

- LSM 主链路已经具备 WAL、MemTable、SSTable、Manifest、Flush、Recovery、Retention 和 Level Compaction。
- SSTable 已采用二进制列式组织，并有 magic、format id、checksum、component 校验和文件格式文档。
- 写入侧已支持 typed batch、wide10 压测、snappy/lz4/zstd payload compression、shard-aware 数据分布和 compaction 后查询验证。
- 内存治理已有 `StorageMemoryOptions`、软硬阈值、写入/flush/query/compaction/compression reservation 和 RSS/runtime gap 指标。
- 元数据已经抽象为 `MetadataStore` 接口，本地实现为 `LocalMetadataStore`。
- 服务化已有 `/metrics`、`/healthz`、`/readyz`、可选 `/debug/pprof/` 和 `/admin/compact` 基础端点。
- 查询系统已有 querylang、queryanalyzer、queryplanner、queryoptimizer、queryphysical、queryexec、queryservice 七层包边界。

## P0 阻塞商用项

### P0-1：可靠性和异常故障矩阵还没有生产级证明

专项一要求覆盖 WAL、Manifest、SSTable、Flush、Compaction、Retention、Recovery 的关键失败点，并且每个故障用例都要包含重启恢复验证。当前已有 fault tests 和恢复协议文档，但仍缺少一张完整矩阵，把每个失败点、测试路径、重启后状态、Manifest/WAL/part 一致性断言全部映射起来。

商用数据库最怕的不是正常写入失败，而是“返回成功后数据不可恢复”或“恢复时静默丢数据”。这一项未完全闭环前，不建议声明商用。

### P0-2：查询系统还不是完整商用查询主链路

七层查询包边界已经建立，但当前计划文档明确说是兼容式分层引入，不直接替换 Engine 查询主链路。`queryoptimizer` 仍偏基础预算与下推标记，`queryphysical` 仍偏 operator 描述，`queryservice` 仍通过兼容执行器接旧查询接口。

商用查询需要完整覆盖 tag/field/time/series/page 下推、聚合、窗口、limit/offset 早停、cancel、deadline、profile/explain、错误分级、读放大预算和复杂语义一致性。当前具备基础，不足以对外承诺完整查询能力。

### P0-3：长期稳定性和 soak 证据不足

shard-aware 10M compact 口径下已有良好数据：写入 + flush `21.937s`，compaction `16.988s`，cold query 2000 行 `14.074ms`，RSS peak `308.6MiB`，SSTable `2534 -> 116`。但这仍是单轮规模测试，不是长期多小时或多天的 write/query/compact/restart/recovery 混合 soak。

商用需要证明 RSS、heap、GC、read amplification、write amplification、space amplification、compaction backlog、query latency 在长期运行中不漂移、不累积、不退化。

### P0-4：测试覆盖率未达到项目硬门禁

AGENTS.md 要求代码行覆盖率达到 `>=90%`。本轮 `go test ./... -cover` 虽然全部通过，但多个核心包低于 90%，尤其是 `internal/engine`、`internal/sstable`、query 七层相关包和 `cmd/mts-storage`。这是明确的工程门禁未达标。

### P0-5：生产安全边界不足

服务层已有 metrics、health、ready、pprof 和 admin compact，但目前没有看到认证、鉴权、TLS、管理端点权限模型、安全默认配置和审计落地策略的完整闭环。尤其是 pprof 和 admin compact 在生产环境必须默认收敛，否则会带来敏感信息泄露和高危管理操作暴露风险。

## P1 商用前必须增强项

### P1-1：Compaction 长稳和放大控制还需继续证明

当前 shard-aware compaction 已明显修正早期单 shard 全量压缩问题，但还需要覆盖后台 compaction 长期调度、backlog drain、级联 compaction、多 shard 并发、磁盘空间不足、retention 并发 reader、读放大触发调度等场景。

### P1-2：内存治理需要覆盖所有热路径和小内存场景

已有 storage memory limiter 是正确方向，但商用还需要证明所有可控内存路径都纳入预算，包括 WAL buffer、flush 编码、compression workspace、compaction merge、query materialization 和服务层请求缓冲。还需要小内存配置下的拒写、降载和恢复测试。

### P1-3：文件格式治理有基础，但格式演进策略还不完整

文件格式文档已经描述 envelope、WAL、Manifest、SSTable part 的 binary layout 和校验规则。恢复协议也有 check/repair/migrate 描述。但商用还需要明确在线升级、离线迁移、回滚、未知格式处理、格式兼容策略和工具演练报告。

### P1-4：元数据接口化完成基础，但缺少分布式一致性实现

`MetadataStore` 和 `LocalMetadataStore` 已经落地，可以作为本地实现。但商用如果要支持多节点、HA 或多租户，需要 ETCD/ZooKeeper/Consul 等外部元数据后端，且要定义 schema 变更、租约、并发 DDL、leader fencing 和一致性语义。

### P1-5：备份、快照和恢复演练不足

当前有 storagecheck、repair、migrate 和恢复协议，但缺少完整 snapshot backup/restore、增量备份、PITR、跨版本恢复、损坏数据目录恢复演练和恢复耗时基线。

## P2 产品化和生态短板

- 外部 API/协议层还不完整：当前更像 Go library + internal service，缺少稳定 HTTP/gRPC/line protocol 写入与查询 API、错误码协议、多租户和限流模型。
- 分布式和 HA 能力缺失：没有副本、leader/follower、分片调度、故障转移、数据再平衡和跨节点 repair。
- 发布工程不足：需要 CI gate、coverage gate、benchmark regression gate、Docker、多平台 release、GoReleaser、制品签名和版本发布流程。
- 可观测性还需要生产集成：metrics 文档已有，但还缺 dashboard、alert rules、trace/profile 安全开关、日志字段规范和容量规划模板。
- 运维手册和 SLO 缺失：需要参数建议、容量估算、磁盘告警、备份恢复手册、升级回滚手册和故障排查 Runbook。

## 建议路线

1. 先补 P0：故障矩阵、查询主链路、长期 soak、覆盖率门禁、服务安全边界。
2. 然后补 P1：compaction 长稳、小内存预算闭环、格式演进、外部元数据、备份恢复。
3. 最后补 P2：API 产品化、HA、发布工程、dashboard/alert、运维 Runbook。

如果目标是“单机嵌入式研发内核”，当前已经具备继续试用和压测的基础。如果目标是“可商用时序数据库产品”，当前还不能宣称达标。
