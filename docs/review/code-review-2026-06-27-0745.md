## 1. `dashboard.go`

### 主要功能
- `go:embed dashboard-dist` 内嵌前端静态资源，构造一个 SPA 静态服务器。
- 对 `/api/`、`/debug/` 未命中资源回 404；其它未命中资源回退到 `/`（`index.html`），实现前端路由。
- 为 `/assets/` 子树设置一年 immutable 缓存。

### 问题分级

#### Critical
- 无。

#### Important
- **`dashboard.go:35` 缓存头判定依赖路径前缀但前缀判定发生在可能被重写之后；对 `/assets/<不存在的文件>` 会先 Fail 取文件后将路径重写为 `/`，结果落入 `index.html`，但 `Cache-Control` 判定仍按原始 `/assets/` 前缀写头。** 当浏览器请求一个被前端引用但部署缺失的 asset（如构建产物不全），会得到 `200 OK + text/html + immutable`，导致前端把 HTML 当作 JS 解析失败同时被长期缓存，无法自愈。建议：回退 `index.html` 时清掉 immutable 头或对 assets 缺失走 404。

#### Minor
- **`dashboard.go:24` 每次 panic 之外的请求都做 `sub.Open` 探测再交给 `http.FileServer` 二次打开，重复 IO。** 单进程 IO 廉价，但嵌入 FS 下每请求多一次 map 查找。可缓存已知路由前缀或在 `http.FileServer` 之上用 `http.StripPrefix` + 自定义 404 处理器替代。
- **`dashboard.go:18` dashboard 未构建时返回 `404` 与纯文本，缺 `Content-Type` 头。** 浏览器按 sniff 行为可接受，但与规范不符。
- SPA fallback 未限制 `req.Method`，HEAD 请求会进入回退逻辑。`http.FileServer` 本身处理 HEAD，但 fallback 后的 HEAD 也会写 `index.html` body，浪费带宽。
- 缺少对 `..` 等异常路径的显式校验，依赖 `sub.Open` 自身防护。Go 的 `io/fs` 已做 `validPath` 校验，但建议增加注释说明此依赖。

### 错误处理
- `dashboard.go:18` 写错误响应使用 `_ = w.Write(...)`，符合规范。

## 2. `http.go`

### 主要功能
- 注册全部 HTTP 路由；挂载 pprof 子树；统一 `apiErrorResponse` 映射。
- 提供 `decodeHTTPJSON`、`writeHTTPJSON`、`writeAPIError`、`requireHTTPMethod`、`splitPath` 工具。

### 问题分级

#### Critical
- 无。

#### Important
- **`http.go:54` pprof 路由 `/debug/pprof/` 用 `adminHTTPHandler` 包裹，但 `/debug/pprof/profile` 等子路由虽经鉴权，pprof 的 `Index` handler 会拼凑 HTML 列出所有子路径，杀伤面比预期大。** 当前已 `cfg.Observability.Pprof.Enabled` + `requireHTTPAdmin` 双门控，但仍建议关闭情况下直接 `http.NotFound`，并生产环境默认禁用（已实现，确认默认值即可）。
- **`http.go:25/30/33/45` 使用 `mux.HandleFunc("/api/v1/admin/databases/", ...)` 这类尾斜杠路径注册，未注册裸路径 `/api/v1/admin/databases`。** 对裸路径请求会落到 `/` 的 dashboard fallback，返回 `index.html` 而非 `404`，语义混乱。建议同时注册裸路径或使用更现代的 `http.ServeMux`（Go 1.22 + pattern）。

#### Minor
- **`http.go:122/136` `looksLikeNotFoundError` / `looksLikeValidationError` 依赖错误字符串模糊匹配。** 一旦底层错误文案不含 `not found` / `invalid` 等关键字就会落到 500，是脆弱映射。建议全局改用具名哨兵错误 `errors.Is`/`errors.As`。
- **`http.go:201` `requireHTTPMethod` 失败时返回 `405` 但 `Code` 写成 `errorCodeBadRequest`，与业务 400 同码，调用方无法区分。** 同时未设置 `Allow` 头（RFC 7231 要求 405 必须带 `Allow`）。
- **`http.go:210` `splitPath` 遇到 `nil` 表示空段，但调用方多处同时使用 `len(parts) == 0` 与 `parts[0] == ""` 两种判空风格。** 建议统一返回 `[]string{}` 并强制调用方判 `len == 0`。
- **`http.go:89` `decodeHTTPJSON` 未限制 body 大小。** middleware 层 `http.MaxBytesReader` 仅在 `MaxRequestBodyBytes > 0` 时生效；未配置时任意大 JSON 可被 `json.Decoder` 慢慢消费，存在资源耗尽风险，应增加默认上限或在 `decodeHTTPJSON` 内 `io.LimitReader`。

### 安全问题
- 路由全量注册，鉴权分散在各 handler；建议显式列出“无需鉴权”的白名单（healthz/readyz/metrics/login/query-stats）以免未来漏鉴权。

## 3. `auth.go`

### 主要功能
- `requireHTTPAdmin` / `requireGRPCAdmin`：Admin Token 或 Bearer 二选一鉴权；空配置回退到开放模式。
- `authorizeHTTPDatabase` / `authorizeGRPCDatabase`：Data Token + 用户身份 + DB 权限三层校验。
- 常量时间比较 token、解析 Bearer、读取 gRPC metadata。

### 问题分级

#### Critical
- **`auth.go:28-36` Admin Token 与 Bearer 优先级存在配置失误回退到“完全无鉴权”的隐患：当 `cfg.Auth.AdminToken == ""` 且 `cfg.Auth.RequireUser == false` 且请求未携带 Bearer 时，`requireHTTPAdmin` 直接 `return nil`。** 这意味着只要运维忘配 `AdminToken` 且未开 `RequireUser`，所有 `/api/v1/admin/*`、`/api/v1/users*`、pprof、flush/compact/storage-snapshot 等危险接口对任意人开放。建议：AdminToken 为空时强制要求 `RequireUser`，缺省即报错，禁止静默开放模式。

#### Important
- **`auth.go:40-45` Admin Token 不匹配后尝试以 Bearer 走 admin 用户校验。** 这相当于“admin token 与 admin 用户 token 任一通过即放行”，扩大了攻击面，且日志中只有一次 `requireHTTPAdmin` 调用记录，无法区分两种放行路径。建议：admin token configured 时优先只比对 admin token，不相等直接 401；若希望 admin user bearer 也能进，应显式在配置中开 `allow_bearer_admin`。
- **`auth.go:247` `constantTimeEqual` 先对参数 `TrimSpace`，再用 `len(want) != len(got)` 早返回。** 该早返回本身泄漏 length 信息，常量时间比较的意义被削弱；同时 `provided := bearer` 路径下，若 admin token 与用户 bearer 长度相同会进入 `subtle.ConstantTimeCompare`，否则瞬时返回。建议：用 `subtle.ConstantTimeCompare` 直接对原串比较，长度差异由其内部处理；或对比较结果统一 `== 1` 判定。
- **`auth.go:163-176` `authenticateHTTPDataUser` 在 `Authorization` Bearer 为空且未开 `RequireUser` 时直接信任 `X-MTS-User` 请求头作为用户名。** 这是“显式身份注入”，任何客户端可伪造任意 `user_name` 写数据 / 查数据，权限检查形同虚设。该模式仅在 `RequireUser=false` 才生效，但仍是默认风险面。建议：将头部信任模式移到独立配置项 `allow_header_user_identity` 并默认关闭。

#### Minor
- **`auth.go:244` `bearerToken` 仅以 `strings.ToLower` 判前缀，再从原串 `value[len("bearer "):]` 截取。** 当客户端传 `Bearer\t...` 或 `BEARER  ` 多空格时按当前实现会保留多余空格，下游 `constantTimeEqual` 又 `TrimSpace`，行为勉强一致但脆弱。建议使用 `strings.CutPrefix` + `ToLower` 或 `strings.Fields`。
- **`auth.go:261` `grpcMetadataValue` 只取第一个值，多值 header 静默丢弃。** gRPC metadata 允许同 key 多值；建议若 >1 视为错误。
- **`auth.go:233` `matchesAnyToken` 在 `subtle.ConstantTimeCompare` 的早返回下，循环匹配多 token 时是否短路取决于实现，仍泄露有效 token 长度信息。** 多 token 场景建议全部比较后聚合结果。

### 错误处理
- `requireUserRole` 在 `err != nil` 时直接返回原始 error，未包成 `apiError`，最终落到 `apiErrorResponse` 走字符串匹配，可能误判为 500。

## 4. `audit.go`

### 主要功能
- 有界环形缓冲（默认 256）+ 持久化到 `_internal.audit_log` measurement。
- `list(userName)` 取对应用户的事件并稳定排序。

### 问题分级

#### Critical
- 无。

#### Important
- **`audit.go:53` 持久化在 `record` 中同步调用 `_ = l.persistEvent(event)`，错误被丢弃。** 该错误路径下 `_ =` 符合 CLAUDE.md “可用 `_` 忽略”，但被忽略的真实后果是审计事件可能静默丢失，违反审计“不可丢失”语义。建议：失败时落 error logger 或 fallback 到本地 ring buffer 的 dead-letter 区。
- **`audit.go:38-54` `record` 在持锁后解锁、再同步调用 `persistEvent`，`persistEvent` 内部执行 `CreateDatabase(ctx, "_internal")` + `engine.Write`，单次审计事件阻塞 HTTP 处理用于 5s 超时窗口。** 每次写操作 / 管理动作会串联一次磁盘 IO 与锁竞争，对写热点路径造成显著延迟放大，是明确的性能问题。建议：改为异步 channel + worker，或允许配置 `audit_persist=false`/`audit_async=true`。
- **`audit.go:62` `CreateDatabase` 在每次审计事件都调用一次。** 即便 `LocalMetadataStore` 内部 idempotent，仍带来元数据锁竞争与日志噪声。建议：启动时创建一次 `_internal`，`persistEvent` 只写点。
- **`audit.go:60` `persistEvent` 使用 `context.Background()` 而非请求 ctx，5s 超时硬编码。** 客户端断开后审计仍阻塞 goroutine；建议使用请求 ctx（带兜底）或可配置超时。

#### Minor
- **`audit.go:48` 截断使用 `append([]auditEvent(nil), l.events[len-l.limit:]...)` 每超限一次重新分配。** 可改成 `l.events = l.events[1:]` 或环形索引以避免大缓冲下重复复制；当前 limit 较小影响小。
- **`audit.go:20` `auditLog.engine *mts.Engine` 未做并发读写保护，但指针本身只读，OK；不过 `engine` 在 `openRuntime` 赋值后无锁，建议构造函数注入而非外部赋值。**
- **`audit.go:94` `event.UserName == userName` 全字符串比较，未 TrimSpace；当 `userName == ""` 且事件中 user 也为空（如匿名 audit），会被并入；建议按需过滤。**

### 安全问题
- 审计事件以明文写入 `_internal`，密码、token 等敏感字段虽然当前未写入，但 Detail 字段是开放字符串，调用方可能误把密码或 token 塞进 Detail。建议在 `record` 前对 Detail 做敏感词脱敏。

## 5. `http_auth.go`

### 主要功能
- 登录：用户名密码 -> token；TTL 可选；记录审计。
- 登出：Bearer 或 body.token -> RevokeToken；忽略验证失败。
- 改密码：Bearer 验证 + 用户名匹配 + ChangePassword。

### 问题分级

#### Critical
- 无。

#### Important
- **`http_auth.go:55-63` 登出在 `VerifyToken` 失败时静默继续 `RevokeToken` 并返回 `200 OK`。** 用户问题“logout handler 是否正确处理了 token 验证失败的情况”：当前实现是“忽略错误，仍然 revoke 并返回成功”，对客户端而言登出永远成功，但存在两个隐患：
  1. `RevokeToken` 的返回错误也被 `_ =` 忽略，真正撤销是否生效无法得知。
  2. 攻击者可对任意随机串调用 `/api/v1/auth/logout` 制造海量 RevokeToken 调用，触发 `_internal` 大量审计写与元数据操作。建议：对完全无效的 token（VerifyToken 失败）返回 401 并跳过 Revoke，仅在 token 合法时撤销；对 RevokeToken 的失败也要返回非 2xx。

- **`http_auth.go:23-25` `TTLSeconds > 0` 时直接构造 `time.Duration`，未设上限。** 客户端可传 `TTLSeconds = 1<<62` 制造近乎永不过期的 token；建议在服务端上限内 clamp（如 max=30d）。

#### Minor
- **`http_auth.go:34` 登录审计 `Action: "login"` 不带失败链路。** 失败路径在 31 行直接返回，无失败审计，难做暴力破解追溯。建议失败也记录 `"login_failed"`。
- **`http_auth.go:74-78` 改密码 API 同时存在 `http_users.go:129 handleUserPassword`（admin 直接 set password）。** 两条路径行为不同（一个验证旧密码，一个不验证），命名易混。建议在 API 文档中明确区分。
- **`http_auth.go:84` `strings.TrimSpace(req.UserName) != principal.UserName` 比较，但 `principal.UserName` 内部可能已 trim，前后不一致风险低。** 可统一在 engine 内做规范化。

### 错误处理
- `ChangePassword` 失败统一映射为 `errorCodeUnauthenticated "invalid credentials"`。当真实原因是 `ErrUserNotFound` / `ErrUserDisabled` 时被掩盖为 401，建议区分 `not_found` -> 404 / `disabled` -> 403。

## 6. `http_meta.go`

### 主要功能
- 管理面：admin 数据库列表 / 创建 / 删除 / 保留策略。
- 数据面：数据库下的 measurements / fields / series 元数据。

### 问题分级

#### Critical
- 无。

#### Important
- **`http_meta.go:112` `r.authorizeHTTPDatabase(..., "read")` 使用字符串字面量 `"read"` 而非 `mts.DatabasePermissionRead`。** 当前 `DatabasePermission` 是 `string` 类型且字面量恰好匹配，运行正确；但任何后续重命名枚举都会静默破坏鉴权。**这是隐蔽的“魔法字符串”安全风险**，必须改用常量。
- **`http_meta.go:99` `handleDataDatabase` 仅在 `requireHTTPMethod` 通过后再 `splitPath`，但 `len(parts) < 2` 时返回 `400 "metadata path is incomplete"`。** 对 `/api/v1/data/databases/`（空段）也会落到此处，建议区别对待：path 完全空时返回 400 比较合理，但同时存在裸路径未注册（见 http.go 问题）。
- **`http_meta.go:126` `len(parts) >= 4 && parts[1] == "measurements"` 分支不校验 `parts[3]` 之外更多段是否合法。** 例如 `/databases/db/measurements/m/fields/extra` 也会进入 `fields` 分支并忽略 `extra`，可对未知资源静默成功。建议截断校验：`len(parts) == 4`。

#### Minor
- **`http_meta.go:33/50/94` 方法不匹配返回 `400 errorCodeBadRequest` 而非 `405`。** 没有使用 `requireHTTPMethod`（它返回 405），整个文件风格不统一。
- **`http_meta.go:151` `queryTags` 仅取每个 key 的 `value[0]`，多值 query 静默丢后值。** 建议显式拒绝多值或 join。
- **`http_meta.go:30/57/84` 审计 `r.auditUser(request)` 调用 `authenticateHTTPDataUser`，会走 `VerifyToken`。** 一次管理请求相当于多了一次 token 校验（鉴权已校验过一次），轻微重复 IO。

## 7. `http_admin.go`

### 主要功能
- 一大堆 admin handler：metrics、api spec、validate/reload config、storage validate/snapshot/export、flush/compact/retention、maintenance、storage memory/compaction stats、admin health、downsample policies/actions。
- 包含 `unixFlexible` / `unixSecondsOrNow` / `timeNow` 等时间工具。

### 问题分级

#### Critical
- 无（鉴权均由 `requireHTTPAdmin` 把守，但鉴权本身存在 auth.go Critical 隐患）。

#### Important
- **`http_admin.go:10-19` `handleMetrics` 无鉴权。** Prometheus 输出通常包含大量内部指标（go_*, process_*, mts_*），可能泄漏引擎规模与负载，生产环境建议加 admin token 或配置白名单。
- **`http_admin.go:344-413` `handleDownsampleAction` 对 `enable` / `disable` / `reset` 三个分支在 `writeActionOK` 后无条件执行 `r.audit.record(...)`，即使操作失败（已写错误响应）也会写一条“成功语义”审计。** 这违反审计正确性。例如 `enable` 失败时 `writeActionOK` 已写 4xx/5xx，但下一行仍记录 `Action: "enable_downsample_policy"`。建议把 `r.audit.record` 移到 `writeActionOK` 成功分支内，或显式 `if err == nil`。
- **`http_admin.go:363-393` `run` / `run-range` / `repair` 等分支的审计记录不对称：** `run` 仅在 `err == nil` 时记录，而 `run-range` / `repair` 完全不记录，`dry-run` 也不记录。审计覆盖不一致，难追溯操作历史。
- **`http_admin.go:327-333` `handleDownsamplePolicyResource` 在 DELETE 分支忽略 `decodeHTTPJSON` 的错误：`_ = decodeHTTPJSON(request, &req)`。** 若客户端发送非法 JSON，`req.Options` 保留零值继续执行 `DropDownsamplePolicyWithOptions`，与调用者意图不符。建议显式辨明：缺 body 视为无 options，非法 body 应 400。
- **`http_admin.go:443` `unixFlexible` 用固定阈值 `100*365*24*time.Hour/time.Second` 区分秒/纳秒。** 阈值 magic number 且单位运算依赖 `time.Second`；建议抽常量并写注释。

#### Minor
- **`http_admin.go:466` `auth.admin_token` 描述写“空值表示开发兼容模式”，但这正是 auth.go Critical 隐患的文案背书。** 修复后需同步更新描述。
- **`http_admin.go:120-136` `healthMetrics` + `intMetric` 用字符串拼接 Prometheus 文本。** 无 escape，若后续 health 字段含用户输入会破坏格式；当前字段都来自内部，OK，但建议复用现有 `metrics` helper。
- **`http_admin.go:165` `handleConfigSchema` 返回的 schema 是硬编码列表，与真实 config struct 字段无强制关联，易漂移。** 建议从结构体 tag 反射或随 struct 改动加 lint 断言。
- **`http_admin.go:265` `handleDownsamplePolicies` 在 `requireHTTPAdmin` 之后直接 `switch request.Method`，但 DELETE 未列出 -> 走 default 返回 400；DELETE 资源的实际路径在 `/api/v1/admin/downsample/policies/`，容易混淆。** 建议明确 405 + Allow 头。

## 8. `http_users.go`

### 主要功能
- 用户列表 / 创建 / 单用户 GET/PUT/DELETE。
- 子资源：`password`、`database-permissions`、`audit`。
- `authz/database/check` 预检。

### 问题分级

#### Critical
- 无。

#### Important

## 9. `http_data.go`

### 主要功能
- 写：`handleWrite`（JSON points）、`handleWriteTyped`（列式批）。
- 查：rows / columns / explain / stats / stream，统一通过 `decodeAuthorizedQuery`。

### 问题分级

#### Critical
- **`http_data.go:19` + `165-172` `writeRequestDatabase` 仅返回第一个 `point.Database != ""` 的数据库，鉴权只校验该库；但 `engine.Write` 会把每条 point 写入它各自 `Database` 字段。** 攻击者可在一次请求里混合多个 database：第一个用授权库通过校验，其余 point 指向未授权库即可绕过写入。这是**多库越权写入**。必须改为：所有 point.Database 取并集，逐一授权；或禁止同一批涉及多个库（与 typed batch 的单库语义对齐）。修复后补集成测试覆盖混合库否定用例。

#### Important
- **`http_data.go:104-109` `handleQueryStats` 无任何鉴权，公开暴露 `QueryStatsSnapshot`。** 虽然 QueryStats 主要为聚合统计，但其中可能包含 `Errors`、`Budget` 等内部状态，建议加 admin token 或与 `/metrics` 一致策略。
- **`http_data.go:165-172` `writeRequestDatabase` 在所有 point.Database 均为空时返回 `""`。** 进而触发 `authorizeDatabase` 的回退到 `config.Engine.DefaultDatabase` —— 该回退写入与显示的“默认库”一致，但鉴权基于“空库名”的 read/write 权限授予，需要确认 engine 的权限模型是否允许用空字符串授权默认库；若不允许则所有未带 database 的写入都会被拒，反之则 silent。建议显式把空库归一化为 `DefaultDatabase` 后再鉴权与写。

#### Minor
- **`http_data.go:130-135` `handleQueryStream` 在 `encoder.Encode` 失败时直接 `return`，但未记日志，磁盘满 / 客户端断开难以排查。**
- **`http_data.go:124` `defer rows.Close()` 在 handler 末尾 OK，不在 for 循环内，符合 CLAUDE.md。**
- **`http_data.go:140-141` stream 结束写 `stats` 与 `end` 两次 Encode；若客户端中途断开，仍会尝试写 error/end，浪费但不致命。**

## 10. `middleware.go`

### 主要功能
- 注入 `X-Request-ID`、安全响应头、请求超时、body 大小上限、并发信号量、metrics 观测、access log。

### 问题分级

#### Critical
- 无。

#### Important
- **`middleware.go:35-39` 超时 `context.WithTimeout(ctx, timeout)` 设置后用 `defer cancel()`，但 `request = request.WithContext(ctx)` 之后的 handler 收到的是带超时的 ctx，OK；不过 `cfg.Limits.RequestTimeout==0` 时不 cancel，行为可接受。** 主要问题是：超时触发后 `http.Server` 不会自动响应 504，handler 内的 engine 调用会因 `ctx.Err()` 返回错误，但响应仍由 handler 处理为业务错误（400/500），客户端难以区分“业务错”与“超时”。建议超时统一映射 504。
- **`middleware.go:45-48` `r.acquireHTTP(writer, httpSem)` 失败时直接 `writeHTTPJSON(429)` 并 `return`，但 `defer releaseHTTP(httpSem)` 仅在成功 acquire 后才注册。** 当前代码先判断 `!r.acquireHTTP(...) { return }`，未进入 defer，行为正确；但代码顺序稍具迷惑性，建议改为显式 `if acquired { defer releaseHTTP(httpSem) }`。
- **`middleware.go:122-126` `httpRoute` 直接以原始 URL.Path 作为 metrics 标签，未做模板化（如 `/api/v1/users/<id>` -> `/api/v1/users/:name`），导致高基数。** 当前 user name / db name 都进 path，metrics 会爆炸。建议在 route 层做 pattern 归一化。

#### Minor
- **`middleware.go:50` `statusRecorder` 仅覆写 `WriteHeader`，未覆写 `Flush` / `Hijack` / `Push`。** 对 SSE/stream handler（`handleQueryStream`）调用 `http.Flusher.Flush()` 不会同步状态，recorder.status 可能停留在 200。实际 handler 不 Flush，影响小。
- **`middleware.go:117-120` `WriteHeader` 多次调用会覆盖 `r.status`，与 net/http “首次 WriteHeader 生效”语义不同。** metrics 中记录到的是最后一次，通常 200 OK no-op，OK。
- **`middleware.go:53` `r.metrics.observe` 传入 `strconv.Itoa(recorder.status)`，每请求构造字符串。** 可缓存常用状态字符串。

### 安全问题
- 设置 `X-Content-Type-Options: nosniff` 与 `X-Frame-Options: DENY` 良好；缺 `Content-Security-Policy`、`Referrer-Policy`、`Strict-Transport-Security`（后者依赖 TLS，可加）。

## 11. `runtime.go`

### 主要功能
- `serverRuntime` 结构；`openRuntime` 引导 engine、admin、audit、http/grpc server。
- `bootstrapDefaultAdmin`：默认 admin/admin。
- `applyLimitState`：构造并发信号量。
- `currentConfig` / `currentLogger` / `setLogger` 读写锁。
- `write/query/flush/compact/applyRetention/maintenanceErrors` 等运行时业务封装。
- `shutdown`：HTTP Shutdown + gRPC GracefulStop + engine.Close。

### 问题分级

#### Critical
- **`runtime.go:84-87/89-109` `bootstrapDefaultAdmin` 使用硬编码默认 `admin/admin` 创建管理员。** 当 `RequireUser=true` 且 `PasswordAuthDisabled=false` 且尚无 admin 用户时，会以弱口令 `admin` 建号。若运维首次启动后未立即改密，结合 admin token 留空开放模式（auth.go Critical），会构成完全无鉴权 + 弱口令的“双重暴露”。建议：仅在显式配置 `auth.bootstrap_admin_password` 时创建，否则启动失败；或首次启动随机生成密码并打印一次到 stderr。

#### Important
- **`runtime.go:329-331` `effectiveConfig` 直接返回 `r.config` 而未加 `RLock`。** 与 `currentConfig()` 行为不一致，且 `handleConfig` 通过 `r.effectiveConfig()` 暴露给 `/api/v1/admin/config`。若与 `setConfig`/reload 并发，存在 data race（`go test -race` 可命中）。建议复用 `currentConfig()`。
- **`runtime.go:55/56` `runtime := &serverRuntime{...}` 中 `audit: audit`（已 set `audit.engine = engine` 在 49 行）。** 但 `auditLog` 字段 `engine` 是外部赋值的（`audit.engine = engine`），CLAUDE.md 倾向构造注入；可改成 `newAuditLog(256, engine)`。
- **`runtime.go:145-175` `start()` 中 `net.Listen` 失败直接返回 error，但若 http 已启动成功而 grpc `Listen` 失败，http 的 goroutine 已在后台 `serveHTTP`，`start` 返回错误后调用方不会 `shutdown` http，造成 goroutine / 端口泄漏。** 建议失败时回滚已启动的服务。
- **`runtime.go:60-62/77-79` `buildTLSConfig` / `newGRPCServer` 失败时 `_ = engine.Close(ctx)` 关闭 engine，但未关闭已构造的 `httpServer`。** 虽然 http 尚未 Listen，影响有限，但仍建议统一 shutdown。

#### Minor
- **`runtime.go:184-189` `reportServeError` 用 `select { case r.serveErr <- err: default: }`，缓冲 2；超过 2 个错误静默丢弃。** 一般够用，建议加日志。
- **`runtime.go:195-217` `shutdown` 先 `httpServer.Shutdown` 再 `grpcServer.GracefulStop`，最后 `engine.Close`。** 顺序合理；但 http shutdown 与 grpc stop 并行执行可能更优雅。当前串行可接受。
- **`runtime.go:308-315` `maintenanceErrors` 变量名 `errors` 遮蔽 `errors` 包；一旦后续在此函数内调用 `errors.Is` 将编译失败。** 建议改名 `errs`。
- **`runtime.go:124-131` `setLogger(nil)` 静默返回，无日志告知调用方，易误配置。**

## 横切问题汇总

### 全局方法检查完整性

按“HTTP 方法是否完整校验”梳理：

| Handler | 方法校验方式 | 风险 |
| --- | --- | --- |
| `handleLogin` / `handleLogout` / `handleChangePassword` | `requireHTTPMethod` (405) | OK |
| `handleHealth` / `handleMetrics` / `handleAPISpec` / `handleErrorCodes` / `handleConfig` / ... 大部分 admin | `requireHTTPMethod` (405) | OK |
| `handleAdminDatabases` | switch + default 返回 400 | 不一致，应为 405 + Allow |
| `handleAdminDatabaseResource` | 直接 `if request.Method != Delete`，其它走子分支没有 default | DELETE 之外的 method 会被错路由到 retention 分支 |
| `handleRetentionPolicies` | switch POST/GET/default 400 | 应 405 |
| `handleDataDatabase` | `requireHTTPMethod` GET | OK |
| `handleUsers` | switch POST/GET/default 400 | 应 405 |
| `handleSingleUser` | switch GET/PUT/DELETE/default 400 | 应 405 |
| `handleDatabasePermissionResource` | switch PUT,POST/DELETE/default 400 但成功路径共享 `writeHTTPJSON` | 应 405；且最后 `writeHTTPJSON(200)` 在 default 之后会被执行，**default 分支已 `return` 缺失？实际 default 调 `writeAPIError` 后未 `return`，会继续执行 `writeHTTPJSON(200)`，造成双写响应**。 |
| `handleDownsamplePolicies` | switch POST/PUT/GET/default 400 | 应 405 |
| `handleDownsamplePolicyResource` | DELETE 单独校验，其余走 POST | OK，但非 POST 返回 400 |
| `handleAuthzDatabaseCheck` | `requireHTTPMethod` POST | OK |

**Critical 风险**：`handleDatabasePermissionResource` (`http_users.go:184-188`) 的 `default:` 分支执行 `writeAPIError(writer, newAPIError(errorCodeBadRequest, "method not allowed", nil))` 后未 `return`，函数末尾 `writeHTTPJSON(writer, http.StatusOK, okResponse{OK: true})` 会被继续调用一次 → 对同一 response 写两次状态行，触发 `http: superfluous response.WriteHeader call` 警告且响应体混乱。需在 default 分支补 `return`。

### 错误处理一致性
- `writeAPIError(newAPIError(errorCodeBadRequest, err.Error(), err))` 模式大量重复，且把内部 error 字符串原样外暴，可能泄漏内部细节。建议对外 message 做白名单映射。
- `decodeHTTPJSON` 失败把 `err.Error()` 直接放进响应，对 `DisallowUnknownFields` 错误明文回显字段名，信息泄漏低但风格不一致。

### 安全建议
1. `auth.go` Critical：admin token + RequireUser 默认开放模式改成默认失败。
2. `runtime.go` Critical：默认 admin/admin 改成强制配置 / 随机生成。
3. `http_data.go` Critical：多库越权写入必须修。
4. `http_auth.go` Important：登出对无效 token 应返回 401；RevokeToken 错误不再忽略。
5. 全局增加 `/metrics`、`/api/v1/data/query/stats` 的鉴权或白名单策略。
6. 审计 `Detail` 增加脱敏；admin 改密等敏感操作失败也需审计。

### 性能建议
1. `audit.go` 持久化改异步 + 启动一次 CreateDatabase。
2. `middleware.go` httpRoute 高基数归一化。
3. `http_meta.go` 重复 `VerifyToken`（auditUser）合并到鉴权阶段复用 principal。

### 代码风格
1. 方法不匹配统一用 `requireHTTPMethod`（405 + Allow 头）。
2. `errors.Is` 替换 `==` 比较 sentinel。
3. `mts.DatabasePermissionRead` 替换字面量 `"read"`。
4. `errors.Join` 替换“回滚失败丢原错误”。
5. `effectiveConfig` 复用 `currentConfig`。
