# MTS 重复代码与精简机会检视报告

检视时间：2026-06-27 15:40

检视范围：当前 MTS 项目生产代码、`cmd/mts-server`、主要测试与 e2e/scale/fault 工具代码。重点关注重复代码抽取、HTTP/gRPC 内部逻辑合并、魔法字符串常量化、错误处理可读性、泛型化机会。

## 总体结论

当前项目整体模块边界已经比前几轮清晰。本轮已完成通用 map/slice clone 与 key 排序函数、`cmd/mts-server` HTTP/gRPC 权限和错误映射重复、HTTP 路由和 gRPC 方法定义字符串硬编码、HTTP JSON helper、以及局部测试 helper 的收敛。测试代码重复只做包内低风险整理，不做跨包测试工具包。

建议不要创建一个无边界的顶层 `utils` 包。Go 项目里更建议按职责创建小包，例如：

- `internal/collections`：泛型 map clone、sorted keys、set helpers。
- `internal/transport/httpjson` 或 `internal/httpx`：JSON decode/write、method guard。
- `cmd/mts-server` 内部新增 endpoint/operation registry：合并 HTTP/gRPC 薄包装和路由常量。

## P0：应优先处理

### 1. 多模块重复实现 `cloneStringMap`、`cloneFieldMap` 和 map 克隆逻辑

状态：已处理

处理结果：新增 `internal/collections`，提供 `CloneMap`、`CloneMapNilIfEmpty`、`CloneSlice`、`CloneSliceNilIfEmpty` 和 `SortedKeys`，已替换报告列出的 map/slice 浅拷贝调用点。深拷贝业务对象保留在所属模块，避免错误泛化。

位置：

- `convert_values.go:113`
- `internal/wal/encoding.go:965`
- `internal/queryexec/row_merge.go:236`
- `internal/queryservice/cache.go:124`
- `internal/user/local_user_helpers.go:92`
- `internal/catalog/key.go:45`
- `internal/querylang/normalize.go:110`
- `internal/engine/query.go:702`
- `internal/observability/metrics.go:96`

问题：

同类 map clone 代码在多个模块中重复，差异主要是 nil/empty 的返回策略：有的 `len == 0` 返回 nil，有的只在 `nil` 时返回 nil。这类差异容易导致 JSON 输出、缓存结果和内部不可变拷贝语义不一致。

建议：

- 新增 `internal/collections`，提供泛型工具：
  - `CloneMap[K comparable, V any](map[K]V) map[K]V`
  - `CloneMapNilIfEmpty[K comparable, V any](map[K]V) map[K]V`
  - `CloneSlice[T any]([]T) []T`
- 对需要深拷贝 value 的场景不要强行泛型化，保留业务函数，例如 `cloneUser`、`clonePasswordRecord`。
- 先统一 nil/empty 语义，再替换调用点，避免 JSON/e2e 快照行为变化。

收益：

减少重复代码，降低 nil/empty 语义分裂风险，后续新增结构不需要反复复制 clone 模板。

### 2. 多模块重复实现 sorted map keys

状态：已处理

处理结果：`internal/catalog`、`internal/engine`、`internal/observability`、`internal/user` 中重复的 string key 排序函数已收敛到 `internal/collections.SortedKeys`。

位置：

- `internal/catalog/metadata.go:138`
- `internal/catalog/metadata.go:147`
- `internal/catalog/downsample.go:377`
- `internal/catalog/downsample.go:386`
- `internal/engine/downsample_executor.go:468`
- `internal/observability/prometheus_text.go:71`
- `internal/user/local_user_helpers.go:13`
- `internal/user/local_user_helpers.go:22`
- `internal/user/local_user_helpers.go:31`
- `internal/user/local_user_helpers.go:40`

问题：

排序 key 函数完全同构，只有 map value 类型不同。当前每新增一个 map 类型就复制一遍同样的 `make -> range -> sort.Strings -> return`。

建议：

- 在 `internal/collections` 中提供：
  - `SortedKeys[V any](map[string]V) []string`
  - 如需要支持其他 key 类型，再加 `SortedOrderedKeys[K cmp.Ordered, V any](map[K]V) []K`
- 用 `slices.Sort` 替代 `sort.Strings`，保持 Go 新版本风格一致。

收益：

这是最直接的泛型化收益点，代码更短，行为更统一。

### 3. `cmd/mts-server` HTTP 和 gRPC 的错误映射逻辑重复且存在默认语义不一致

状态：已处理

处理结果：`cmd/mts-server` 已新增 `classifyAPIError`，HTTP 和 gRPC 共用同一错误分类，协议层只负责映射 HTTP status 或 gRPC code。未知错误统一为 HTTP 500 / gRPC `Internal`。

位置：

- HTTP：`cmd/mts-server/http.go:106`
- gRPC：`cmd/mts-server/grpc.go:683`
- HTTP 状态映射：`cmd/mts-server/http.go:143`
- gRPC code 映射：`cmd/mts-server/grpc.go:712`

问题：

HTTP 和 gRPC 各自维护一套 `apiError`、MTS sentinel error、validation-like error 到协议状态的映射。分类规则基本一致，但实现分裂。更明显的是 gRPC 默认分支返回 `codes.InvalidArgument`，而 HTTP 默认是 `500 InternalServerError`，这会导致同一内部错误在 HTTP/gRPC 上语义不同。

建议：

- 抽出一个协议无关分类函数，例如：
  - `classifyAPIError(err error) apiErrorClass`
  - class 包含 `code errorCode`、`message string`、`isInternal bool`
- HTTP/gRPC 只负责把 `errorCode` 转成 `http.Status*` 或 `codes.Code`。
- 错误判断用 `switch { case ... }` 替代长 `else if`，提升可读性。
- 明确未知错误默认策略：HTTP 500，对应 gRPC 应为 `codes.Internal`，除非产品层决定隐藏为 InvalidArgument。

收益：

消除协议错误语义分裂，减少后续新增错误码时漏改一边的风险。

### 4. `cmd/mts-server` HTTP/gRPC 管理面薄包装重复

状态：已处理

处理结果：HTTP route、gRPC method、stream type、bearer prefix 和通用错误消息已常量化；固定 method + admin 鉴权的 HTTP 管理接口已通过 `requireHTTPAdminMethod` 收敛。完整 operation registry 本轮评估后不落地，原因是当前协议层仍有多种资源型路径和审计细节，强行统一注册会带来较大行为回归风险；本轮采用常量化和薄 wrapper 完成低风险收敛。

位置：

- HTTP 管理接口重复方法守卫和 admin 鉴权：`cmd/mts-server/http_admin.go:15` 起
- gRPC 管理接口重复 admin 鉴权：`cmd/mts-server/grpc.go:346`、`cmd/mts-server/grpc.go:432`、`cmd/mts-server/grpc.go:489`、`cmd/mts-server/grpc.go:584` 等
- gRPC method desc 硬编码清单：`cmd/mts-server/grpc.go:110`
- HTTP route 硬编码清单：`cmd/mts-server/http.go:15`

问题：

大量 handler 的结构都是：

1. 检查 HTTP method 或 gRPC admin 权限。
2. Decode 请求。
3. 调用 `serverRuntime` 内部操作。
4. 包装响应或错误。

业务操作已经有部分沉到 `serverRuntime`，但协议层仍手写大量薄包装，重复量高，新增接口时需要同时维护 HTTP route、gRPC method、权限、API spec 和测试路径。

建议：

- 建立内部 operation registry，例如：
  - `operation{Name, HTTPPath, HTTPMethod, GRPCName, AuthScope, RequestFactory, Handler}`
- HTTP/gRPC 都从同一 registry 派生注册，减少手写清单。
- 对 admin 操作提供统一 wrapper：
  - `adminHTTP(method, decode, handle)`
  - `adminGRPC(handle)`
- 数据面操作同理提供 `dataRead`、`dataWrite` wrapper。

收益：

这是 `mts-server` 精简收益最大的点。可以显著降低接口不一致、漏鉴权、漏审计、漏 API spec 的概率。

## P1：建议处理

### 5. HTTP/gRPC 认证与数据授权存在成对重复

状态：已处理

处理结果：新增 `credentialSource`、HTTP/gRPC source adapter 和统一的 admin/data/user 鉴权函数，原 HTTP/gRPC 入口保留为协议适配壳，主体安全逻辑已合并。

位置：

- Admin 鉴权：`cmd/mts-server/auth.go:23` 与 `cmd/mts-server/auth.go:49`
- Data token 鉴权：`cmd/mts-server/auth.go:133` 与 `cmd/mts-server/auth.go:148`
- Data user 认证：`cmd/mts-server/auth.go:163` 与 `cmd/mts-server/auth.go:178`
- DB 授权入口：`cmd/mts-server/auth.go:102` 与 `cmd/mts-server/auth.go:118`

问题：

HTTP 和 gRPC 的差异只是“从哪里取 header/metadata”，后续逻辑完全一致。现在重复维护，容易出现一边修复一边遗漏。

建议：

- 定义一个内部凭据访问接口：
  - `type credentialSource interface { Value(key string) string; Bearer() string; Context() context.Context }`
- HTTP request 和 gRPC metadata 分别适配成 source。
- `requireAdmin(source)`、`requireDataToken(source)`、`authenticateDataUser(source)` 复用同一逻辑。

收益：

减少鉴权重复和安全策略分叉风险。

### 6. HTTP JSON decode/write 在多个包重复

状态：已处理

处理结果：新增 `internal/httpjson`，提供严格 JSON decode 和统一 write helper，已替换 `cmd/mts-server`、`internal/queryservice`、`internal/service` 的重复实现。

位置：

- `cmd/mts-server/http.go:89`
- `cmd/mts-server/http.go:95`
- `internal/queryservice/protocol.go:137`
- `internal/queryservice/protocol.go:229`
- `internal/service/server.go:105`
- `cmd/mts-storage/main.go:134`

问题：

多个包都实现 JSON decode/write。细节包括 `DisallowUnknownFields`、是否关闭 body、Content-Type、错误响应结构不同。业务响应结构可以不同，但基础 decode/write 行为不应重复。

建议：

- 库代码可新增 `internal/httpjson`：
  - `DecodeStrict(request *http.Request, value any) error`
  - `Write(writer http.ResponseWriter, status int, value any)`
  - `RequireMethod(writer, request, method, writeError)` 可选
- `cmd/mts-storage` 是 CLI，不一定要复用 HTTP writer，但 JSON encode 到 stdout/stderr 可单独保留。

收益：

统一 JSON 行为，减少协议 bug 和安全细节遗漏。

### 7. 字符串硬编码需要常量化和分组

状态：已处理

处理结果：`cmd/mts-server/constants.go` 已集中管理 HTTP route、gRPC method、stream type、content type、bearer prefix 和通用错误消息；`internal/queryservice` 与 `internal/service` 使用包内局部常量，避免反向依赖 `cmd`。

位置：

- HTTP route：`cmd/mts-server/http.go:15`
- pprof route：`cmd/mts-server/http.go:60`
- gRPC service/method：`cmd/mts-server/grpc.go:22`、`cmd/mts-server/grpc.go:110`
- Stream record type：`internal/queryservice/protocol.go:151`、`cmd/mts-server/http_data.go:126`
- Auth bearer prefix：`cmd/mts-server/auth.go:216`
- 常见 error message：`"method not allowed"` 在多处出现

问题：

这些字符串是协议契约或跨测试引用点，散落硬编码会增加重命名和路径拆分时的漏改风险。

建议：

- `cmd/mts-server` 增加 `routes.go` / `methods.go` / `constants.go`，分组管理：
  - `routeDataWrite`
  - `routeAdminConfig`
  - `grpcMethodCreateUser`
  - `streamTypeRow/Error/End`
  - `bearerPrefix`
  - `messageMethodNotAllowed`
- 测试尽量引用同一常量，或用 helper 生成 URL。

收益：

降低 API contract 漂移风险。

### 8. 错误处理可用 `switch` 收敛，提高可读性

状态：已处理

处理结果：HTTP/gRPC 错误映射已改为共享分类函数加 `switch`；HTTP/gRPC 权限入口已通过 credential source 收敛。权限枚举校验保持在业务模块和已有接口中，不额外引入重复校验函数。

位置：

- `cmd/mts-server/http.go:106`
- `cmd/mts-server/grpc.go:683`
- `cmd/mts-server/http_users.go:174`

问题：

部分错误处理使用长 `else if` 或嵌套 `if`，在新增错误类型时不易扫描覆盖关系。尤其 HTTP/gRPC 错误映射适合 `switch { case errors.As(...): ... }`。

建议：

- `apiErrorResponse` 和 `grpcError` 改成共享分类函数 + `switch`。
- 权限检查如 `permission != read && permission != write && permission != admin` 可抽成 `isValidDatabasePermission`，或复用 user 模块已有校验逻辑。

收益：

降低复杂条件误读成本。

## P2：低优先级或需谨慎处理

### 9. 测试代码存在大量 open/close/helper 重复

状态：已处理

处理结果：根包和 `internal/engine` 已新增包内测试 helper，并替换首批简单 open/close 模板。复杂错误路径测试保留显式 close 处理，确保失败时仍能报告资源关闭错误。

位置：

- 根包 `engine_test.go` 中多处 `Open -> check err -> Close`
- `internal/engine/engine_test.go` 中多处 `Open(model.Options{Path: t.TempDir(), ShardDuration: time.Hour, MemTableMaxSamples: ...})`
- 多个测试文件中重复 `default/autogen/metrics/cpu`

问题：

测试重复明显，但直接大规模抽 helper 容易降低测试可读性。当前生产代码优先级更高。

建议：

- 针对每个包局部新增 test helper，不做跨包测试 utils。
- 例如 `openTestEngine(t, optsFn)`、`closeEngine(t, eng)`、`testQuery(...)`。
- 常见测试维度可在 `_test.go` 中常量化：`testDatabaseMetrics`、`testRetentionAutogen`。

收益：

减少测试维护成本，但不应优先于生产代码重复治理。

### 10. 二进制 payload reader/writer 的模式相似，但不建议立刻合并

状态：暂不处理

位置：

- `internal/catalog/persist.go`
- `internal/wal/encoding.go`
- `internal/sstable/encoding.go`
- `internal/user/local_user_encoding.go`

问题：

这些文件都有 `payloadReader` / varint / string / byte 读取模式，看起来重复。但它们属于不同持久化格式边界，错误消息和兼容性约束不同。

建议：

- 暂不抽公共框架。
- 只有在后续新增第三个以上新持久化格式，且格式演进策略统一时，再考虑 `internal/codec` 中新增 typed reader/writer。

原因：

过早合并可能把 WAL、Catalog、SSTable、User metadata 的格式演进耦合起来，收益低于风险。

### 11. 顶层 `utils` 包不建议作为默认方案

状态：建议不采用顶层宽泛 utils

问题：

用户提到可以抽 `utils` 包，但顶层宽泛 `utils` 容易成为跨模块依赖垃圾桶，破坏当前刚建立起来的模块边界。

建议：

- 可建 `internal/collections`、`internal/httpjson`、`internal/protocol` 等职责明确的小包。
- 只把纯函数、无业务模型依赖或低层模型依赖稳定的函数抽入公共包。
- 不要把业务校验、协议错误、用户权限这种领域逻辑放进通用 utils。

## 建议实施顺序

1. P0-1/P0-2：新增 `internal/collections`，替换 clone map 和 sorted keys，补泛型工具测试。
2. P0-3/P1-8：抽 `cmd/mts-server` 错误分类函数，HTTP/gRPC 共享错误分类，修正 gRPC 默认 unknown error code。
3. P1-5：抽 HTTP/gRPC credential source，合并 admin/data 鉴权逻辑。
4. P0-4/P1-7：建立 `cmd/mts-server` route/method/operation registry，逐步把 HTTP/gRPC 薄包装迁移到统一注册模型。
5. P1-6：抽 `internal/httpjson`，统一 JSON decode/write 和 method guard。
6. P2-9：最后做测试 helper 收敛，不影响生产逻辑。

## 不建议本轮处理的内容

- 不建议把 WAL/Catalog/SSTable/User metadata 的二进制 reader/writer 立即合并。
- 不建议建顶层宽泛 `utils` 包。
- 不建议跨包统一测试 helper；每个包内部按场景局部整理即可。
