# 查询引擎商用能力差距检视报告

## 检视范围

- 查询专项设计：`docs/superpowers/specs/2026-06-19-commercial-query-builder-design.md`
- 查询语言与 Builder：`query_builder.go`、`internal/querylang/*`
- 查询分析、计划、优化、物理计划：`internal/queryanalyzer/*`、`internal/queryplanner/*`、`internal/queryoptimizer/*`、`internal/queryphysical/*`
- 查询执行：`internal/queryexec/*`
- Engine 与 QueryService 接入：`internal/engine/query*.go`、`internal/queryservice/*`
- SSTable 查询相关路径：`internal/sstable/read.go`

## 总体结论

当前查询引擎已经具备“结构化 Builder + 基础分层计划 + 单机流式扫描”的雏形，可以支撑简单查询、基础聚合、时间窗口、tag/field 过滤、排序、分页和 explain。但与 InfluxDB、Prometheus、VictoriaMetrics、TimescaleDB、IoTDB 这类成熟时序数据库相比，还没有达到商用查询引擎水平。

主要差距不是单点语法，而是三个系统性能力不足：

1. 查询语义不完整：缺 SQL/PromQL 类表达能力、复杂布尔表达式、更多时序函数、跨序列分组合并和补点语义。
2. 优化器与执行器偏薄：当前优化器主要记录 pushdown 标签，不具备成本模型、统计信息驱动、算子重排、TopN/Limit 深度下推和多路有序归并。
3. 生产治理不足：查询 admission、超时、内存 spilling、慢查询、profile、租户隔离、持续压测和兼容性测试还不完整。

## 当前已具备的能力

- Builder 已覆盖 `SELECT/FROM/WHERE/GROUP/ORDER/LIMIT/OFFSET` 基础原语。
- WHERE 支持 time range、tag eq/ne/exists/in、field eq/ne/gt/gte/lt/lte。
- 底层 SSTable 已能按 part、series、field、page 时间范围做过滤。
- QueryService 有基础并发 admission。
- Engine 有 QueryStats、read budget、query memory limit 的初步控制。
- Aggregation 支持 `count/sum/avg/mean/min/max/first/last`。

## 与主流开源时序数据库对比

### InfluxDB

InfluxDB 的查询侧重点是 Flux/InfluxQL 语义、tag/field 条件、window aggregate、selector、fill、derivative、rate 类处理和 storage read pushdown。MTS 当前 Builder 能表达基础语义，但缺复杂表达式、fill、derivative、difference、moving aggregate、selector 族扩展，也缺成熟的 storage aggregate pushdown。

### Prometheus

Prometheus 的核心优势在 PromQL：range vector、instant vector、label matcher、regex matcher、rate/irate/increase、histogram、recording rules 和强大的向量匹配语义。MTS 当前没有 PromQL 或类 PromQL 表达层，也没有 range vector 语义、counter reset 处理、histogram 查询和 label regex matcher。

### VictoriaMetrics

VictoriaMetrics 强项是 MetricsQL、海量 label index、rollup/result cache、查询拆分、并行执行、内存控制和高压缩读路径。MTS 当前还是单机串行/弱并行执行，tag predicate 主要依赖 catalog 集合过滤，field predicate 是 post-filter，缺 result cache、rollup cache、并行 shard/part scan 调度和强制内存上界。

### TimescaleDB

TimescaleDB 依托 PostgreSQL planner/executor，具备成熟 SQL、索引、join、continuous aggregate、chunk pruning、并行查询、事务一致性和权限体系。MTS 当前没有 SQL parser、join、subquery、权限模型、事务级一致性查询语义和连续聚合。

### IoTDB

IoTDB 侧重路径模型、设备/传感器过滤、对齐/非对齐时间序列、downsampling、fill、last query、schema template 和分布式执行。MTS 当前 row merge 对齐能力较基础，缺 fill/interpolation、last query 快路径、设备级路径查询和分布式执行计划。

## P0 必须补齐

### P0-1 查询语义需要从 Builder 原语升级为完整表达树

证据：

- 当前专项明确不支持 SQL parser、复杂布尔表达式和跨 measurement join。
- WHERE 目前多个条件按 AND 组合，不支持 OR。

影响：

- 真实业务常见条件如 `(host='a' OR host='b') AND usage > 80`、regex tag matcher、NOT、nested predicate 无法表达。
- 无法与 InfluxQL、PromQL、SQL 类查询能力对齐。

建议：

- 引入表达式 AST：`And/Or/Not/Compare/In/Regex/Exists/Between`。
- Builder 仍保留，但底层统一产出表达树。
- Analyzer 输出可下推表达式、半下推表达式、post-filter 表达式。

### P0-2 GROUP BY tag 目前没有真正跨 series 合并

证据：

- 设计文档说明 `GROUP BY tag` 只在计划中保留，不在本轮跨 series 合并 tag group。
- Planner 会生成 GroupNode，但执行层聚合按 `ColumnSeries` 独立处理。

影响：

- `GROUP BY region` 这类查询会按 series 输出，不能把相同 tag key 的多条 series 聚成一个 group。
- 与 InfluxDB、Prometheus/VictoriaMetrics 按 label group 聚合的行为存在明显差距。

建议：

- 新增 group aggregate executor。
- 按 group key 维护聚合状态，避免全量 materialize。
- 支持 `by(...)`、`without(...)` 类 group key 语义。

### P0-3 聚合和时序函数覆盖不足

证据：

- Analyzer 函数白名单只有 `count/sum/avg/mean/min/max/first/last`。
- 聚合执行只处理上述函数。

影响：

- 缺 `rate/irate/increase/difference/derivative/stddev/stdvar/percentile/quantile/topk/bottomk/mode/median/spread/elapsed/moving_average` 等常用函数。
- 缺 counter reset、空窗口、NaN、Inf、缺失值和字符串/布尔 selector 的完整语义。

建议：

- 分层实现：selector、aggregate、rollup、transform 四类函数。
- 每个函数明确输入类型、输出类型、窗口边界、空值策略和 counter reset 规则。
- 建立函数语义兼容测试矩阵。

### P0-4 field predicate 仍是后过滤，读放大高

证据：

- Engine 将 field predicate 放入 `PostFilterPredicates`。
- 执行链路先扫描并装饰列，再通过 `NewFilteredColumnStream` 或 `NewFilteredRowStream` 过滤。

影响：

- `WHERE value > 90 LIMIT 2000` 可能需要读取大量 page/value block 后才能筛出目标。
- 对高基数 series 和低选择性条件，CPU、IO、RSS 都容易失控。

建议：

- SSTable page meta 增加数值 min/max、字符串 prefix/dictionary、bool bitmap 统计。
- 对数值比较做 page/block 级跳过。
- 对 tag/field 建立可选二级索引或倒排索引。

### P0-5 ORDER BY time desc 的 row 路径会全量加载排序

证据：

- `orderedRowStream.load()` 会把 source 所有 row append 到内存，再 `sort.SliceStable`。

影响：

- `ORDER BY time DESC LIMIT 2000` 在真实场景下应该优先从最新 shard/page 读取并早停；当前实现可能全量读取、全量排序后再分页。
- 这会直接导致 RSS peak 和查询延迟不可控。

建议：

- 对 desc 查询反向遍历 shard、part、page。
- 用 k-way merge 替代全量排序。
- 对 `ORDER BY time DESC LIMIT N` 建立 TopN/early-stop 执行路径。

### P0-6 Row 查询和查询结果 API 存在 materialize 风险

证据：

- `QueryRows` 将所有 row append 到 slice 后返回。
- `rowMergeStream` 会按 series 把列转换为 row，非对齐列使用 map 聚合 timestamp。

影响：

- 大范围 row query 会占用大量内存。
- 商用系统需要默认 cursor/streaming/page token，不能鼓励一次性全量返回。

建议：

- Public API 优先暴露 iterator/cursor。
- `QueryRows` 只作为小结果 convenience API，并受严格 limit。
- Row merge 改成按时间多路合并，尽量避免 per-series 大 map。

## P1 应尽快补齐

### P1-1 优化器缺成本模型和统计信息

证据：

- `Optimize` 仅检查传入估算是否超预算，并调用 `detectPushdowns`。
- 没有从 catalog、SSTable meta、series cardinality、page stats 生成真实 estimate。

影响：

- 无法做索引选择、算子重排、并行度决策、读放大预测和计划拒绝。

建议：

- 为 measurement、field、tag、shard、part、page 建立统计信息。
- 优化器输出估算读 bytes、samples、series、pages、CPU cost。
- 超预算前置拒绝或改写查询计划。

### P1-2 缺并行查询调度和背压

影响：

- 目前查询主要按 shard/part stream 合并，缺成熟 worker pool、per-query memory token、IO token、优先级和取消传播。
- 与 VictoriaMetrics、IoTDB 等在多 shard、多 part 并行查询上有明显差距。

建议：

- 引入 query scheduler。
- 支持按 shard/part 并行 scan、bounded channel、错误快速取消、优先级和公平调度。

### P1-3 Explain/Profile 仍偏基础

证据：

- QueryService Result 只返回 logical root、physical operator names、pushdowns、基础 stats。

影响：

- 无法定位慢查询到底慢在 catalog、index、page decode、filter、aggregate、sort 还是 output。

建议：

- 为每个 operator 记录输入/输出 rows、samples、bytes、耗时、alloc、跳过 page 数。
- 输出 plan tree，而不是只有 root/operator name。

### P1-4 缺查询缓存和预计算接入

影响：

- 常见 dashboard 查询、固定窗口聚合、最近时间范围 rollup 无法复用结果。
- 与 VictoriaMetrics rollup cache、Prometheus recording rules、Timescale continuous aggregate 存在差距。

建议：

- 引入 result cache 和 rollup cache。
- 后续预聚合专项可作为独立物化层，不直接耦合 SSTable。

### P1-5 查询一致性和快照边界需要更明确

影响：

- 商用查询需要明确查询能看到哪个 memtable、WAL、SSTable、compaction 版本。
- 当前已有 snapshot/catlog、tombstone 和 lifecycle lock，但查询一致性语义还没有文档化、测试矩阵化。

建议：

- 定义 read snapshot version。
- 覆盖 flush/compaction/delete/write 并发下的查询一致性测试。

## P2 中长期增强

- SQL parser 或类 SQL 方言，至少提供兼容 InfluxQL 子集的入口。
- PromQL/MetricsQL 子集，适配指标监控场景。
- Join/subquery/having/distinct/order by field。
- Histogram、summary、distribution 查询。
- Fill/interpolation/downsample alignment。
- 多租户权限、审计、限流和 query kill。
- 分布式 query coordinator、remote read、分片聚合。
- 查询基准体系：固定 100K/1M/10M/100M 数据，覆盖高基数、低选择性、高选择性、宽表、多字段、冷热 shard。

## 优先级建议

1. 先做 P0-5 和 P0-6：解决 desc+limit 和 row materialize 风险，直接降低 RSS peak。
2. 再做 P0-2 和 P0-3：补齐 group aggregate 和常用时序函数，让语义接近时序数据库主流能力。
3. 并行设计 P0-1 和 P0-4：表达式 AST 与 field/page 级索引需要一起设计，否则后面会反复返工。
4. 最后做 P1-1/P1-2/P1-3：让优化器、调度和观测真正能支撑生产排障与容量控制。

## 结论

当前查询引擎是“可继续演进的单机查询基础”，不是“可商用的现代时序查询引擎”。如果要达到商用能力，最关键不是马上做 SQL parser，而是补齐表达式 AST、跨 series group aggregate、常用时序函数、field/page 级下推、desc+limit 快路径、流式结果 API、成本优化器和 operator profile。
