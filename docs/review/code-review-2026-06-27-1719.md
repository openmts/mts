# local_user_adapter.go 模块边界检视报告

检视时间：2026-06-27 17:19

检视范围：根包 `local_user_adapter.go`、`engine_types.go`、`engine.go`、`user_types.go`、`options.go`、`internal/runtime/user.go`、`internal/user`、`internal/engine`。

## 结论

处理状态：已按长期方案处理。

`local_user_adapter.go` 当前不是 public API 暴露：文件在根包但类型和函数均未导出，外部用户不能直接引用 `localUserManager` 或 `openLocalUserManager`。

但从模块化设计看，这个文件确实存在 facade 层实现细节泄漏问题。根包当前直接导入 `internal/runtime` 和 `internal/user`，并在根包内声明 `localUserBackend` 组合 internal 用户模块的细粒度接口。这让根包从“外部 API facade”变成“默认本地用户实现适配层”，不符合后续可商用 SDK 对公共边界简洁性的要求。

本轮处理：已删除根包 `local_user_adapter.go`，默认本地用户管理适配迁移到 `internal/runtime`；根包 `Engine` 只持有 runtime facade，不再分别持有 storage engine 和 user manager；架构门禁已阻止根包重新导入 `internal/user`。

用户管理不建议放进 `internal/engine`。`internal/engine` 当前是存储引擎层，职责应聚焦 WAL、MemTable、SSTable、Catalog、查询、compaction、retention、downsample 等存储能力。用户管理、认证、授权属于运行时/服务治理能力，应该和 storage engine 并列组合，而不是下沉到 storage engine 内部。更合理的位置是 `internal/runtime` 或新增 `internal/application`/`internal/security` 组合层。

## 当前放在根包的历史原因

历史计划 `docs/superpowers/plans/2026-06-24-user-management.md` 明确写过：

- public package 定义 `UserManager`、用户 DTO 和权限 DTO。
- 默认本地实现位于 `internal/user`。
- `local_user_adapter.go` 是根包私有适配器，用于把内部默认实现适配成 public `UserManager`。
- 根包不暴露默认实现类型或构造函数。

因此最初放在根包的直接原因是：public `UserManager` 使用根包 DTO，而 `internal/user.Manager` 使用 internal DTO，需要一个转换适配层。

## 主要问题

### P1-1：根包 facade 直接感知 internal 用户实现细节

状态：已处理

处理结果：默认本地用户适配逻辑已迁移到 `internal/runtime/user_manager.go`，根包只保留 public `UserManager` 注入时需要的薄 adapter。根包不再导入 `internal/user`。

证据：

- `local_user_adapter.go` 直接导入 `internal/runtime` 和 `internal/user`。
- `localUserBackend` 在根包组合了 `internal/user.UserStore`、`PermissionStore`、`CredentialStore`、`Authenticator`、`TokenStore`。
- `openLocalUserManager` 在根包接收 `UserOptions`，调用 `runtime.OpenUserManager`。

影响：

- 根包不再只是 public API facade，还承担默认本地用户模块的适配和装配细节。
- 后续如果 internal 用户接口继续拆分，根包也要跟着变化。
- 用户模块实现细节虽然没有导出给外部用户，但已经泄漏到根包代码结构中。

建议：

- 将 `localUserManager` 适配器迁移到内部组合层，例如 `internal/runtime`。
- 由内部组合层返回根包需要的 public `UserManager` 接口实现。
- 根包 `Open` 只调用一个更高层工厂，例如 `runtime.OpenPublicUserManager` 或 `runtime.OpenEngineRuntime`，不再直接导入 `internal/user`。

### P1-2：Engine facade 同时持有 storage engine 和 user manager

状态：已处理

处理结果：根包 `Engine` 已改为只持有 `*runtime.Engine`。storage engine 和 runtime 用户 manager 由 `internal/runtime.Engine` 组合和关闭。

证据：

- `Engine` 包含 `inner *storageengine.Engine`、`userManager UserManager`、`closeUserManager func() error`。
- `Open` 先打开 `storageengine.Open`，再调用 `openEngineUserManager`。
- `Close` 同时关闭 storage engine 和 user manager。

影响：

- 根包 `Engine` 同时表示“存储引擎 facade”和“带用户系统的运行时 facade”。
- 用户管理方法挂在 `Engine` 上，语义上容易让人误以为用户模块是 storage engine 的内部组成部分。
- 后续服务端运行时如果加入审计、认证中间件、token 策略、外部 IAM，根包 `Engine` 还会继续膨胀。

建议：

- 短期保留 public API 兼容形态，但把默认用户模块的创建和关闭动作移出根包。
- 中期考虑区分嵌入式存储 facade 和运行时 facade：
  - `Engine`：存储能力。
  - `Runtime` 或 `ServerRuntime`：组合 storage engine、user manager、auth/authz、observability。

### P1-3：不应把用户模块放入 storage engine

状态：已处理

处理结果：用户系统没有下沉到 `internal/engine`，而是作为与 storage engine 平行的 runtime 组件组合。架构门禁已阻止 `internal/engine` 依赖 `internal/runtime` 或 `internal/user`。

判断：

不建议将用户管理定义在 `internal/engine`，原因是用户管理不属于存储引擎核心职责。

理由：

- storage engine 应提供数据库、measurement、series、写入、查询、compact、retention、downsample 等存储能力。
- 用户、密码、token、角色、DB 权限属于安全和管理面能力，应该由运行时组合层调用 storage engine 的 metadata/database 能力，而不是成为 storage engine 内部依赖。
- 如果把用户系统塞进 `internal/engine`，会让 engine 依赖安全模块，扩大 engine 职责，和此前“engine 过宽”的检视结论冲突。

建议：

- 用户模块和 storage engine 保持平行模块。
- 上层通过依赖注入组合：
  - `internal/runtime` 负责创建默认本地用户 manager。
  - `cmd/mts-server` 或 runtime facade 负责把请求鉴权、用户权限校验和 storage 操作串起来。
  - `internal/engine` 只暴露必要的存储/metadata 操作。

## 推荐重构方向

### 方案 A：低风险收敛根包适配器

目标：不改变 public API，消除根包对 `internal/user` 的直接依赖。

动作：

- 在 `internal/runtime` 增加一个 public-facing adapter 工厂，但避免形成 internal 反向导入根包的循环。
- 由于 Go 的 `internal` 包不能导入父级根包而不形成循环，直接在 `internal/runtime` 返回根包 `UserManager` 不可行。
- 可新增一个位于根包下但职责更明确的文件名，例如 `user_adapter.go`，并减少它对 internal 细粒度接口的感知。这只能改善命名和局部结构，不能根治 facade 泄漏。

评估：收益有限，不能彻底解决当前问题。

### 方案 B：引入根包内部子目录作为 public DTO 适配边界

目标：降低根包文件污染，但保持 public API。

动作：

- 保留根包 public `UserManager` 和 DTO。
- 将默认本地用户适配逻辑移动到 `internal/runtime/publicuser` 这类包不可行，因为 internal 包导入根包会形成循环。
- 若要做到彻底移动，需要先把 public 用户 DTO/接口从根包拆到独立可导入包，例如 `pkg/api` 或 `internal/publicapi`，但这会引入 public API 变化或更大重构。

评估：当前早期阶段可考虑，但需要完整规格设计。

### 方案 C：推荐，中期拆分 runtime facade

目标：明确 storage engine 与 runtime 的边界。

动作：

- 保留现有 `Engine` 对外方法，短期不破坏用户。
- 新增内部 runtime 结构，组合：
  - `*internal/engine.Engine`
  - `internal/user.Manager` 或第三方 `UserManager`
  - 认证授权策略
  - 配置和观测
- 根包 `Open` 调用 runtime 工厂，并只持有 runtime facade，而不是分别持有 `inner` 和 `userManager`。
- 后续 public API 可以逐步演进为：
  - 嵌入式存储 API：只关心存储。
  - 服务端/runtime API：关心用户、认证、授权、配置和管理面。

评估：最符合长期模块化方向，但需要设计和迁移计划。

## 建议优先级

1. 不要把用户系统下沉到 `internal/engine`。
2. 承认 `local_user_adapter.go` 放根包是历史适配产物，当前不导出但设计上不够干净。
3. 下一轮重构应以 runtime facade 为目标，而不是把文件简单搬到 storage engine。
4. 若只想做局部清理，至少应减少根包直接依赖 `internal/user` 的细粒度接口，把 `localUserBackend` 改成 runtime 层定义的更粗接口或只依赖 `internal/runtime` 暴露的接口。
