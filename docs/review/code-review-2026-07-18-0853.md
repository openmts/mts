## 2. D1：本轮优先深度优化

### EARS-D1-01 查询默认保护

**EARS：**  
当客户端发起查询且未设置 `Limit` 与 `Budget` 时，系统应当应用可配置的默认读取保护（例如默认 `MaxSamples` / 可选默认 `Limit`），并在超限时返回可 `errors.Is` 的 `ErrReadBudgetExceeded` / `ErrResourceExhausted`，而不是允许无界全表扫描耗尽资源。

**验收：**
1. `Options` / public Options 可配置默认 query budget（0 表示不启用，保持兼容或安全默认）
2. `normalizeQuery` 在 budget/limit 为零时注入默认保护
3. 单测覆盖：无 limit/budget 查询触达默认保护
4. 既有显式 budget/limit 行为不变
5. `make test` + e2e + 无性能劣化 >10%

---

### EARS-D1-02 MemTable 乱序降载

**EARS：**  
当同一 series/field 列在短时间内出现高比例乱序/重复追加时，系统应当记录比率指标，并在超过配置阈值时触发更积极的 flush（或等价降载），避免 MemTable 无序膨胀与查询 sort/dedupe 成本失控。

**验收：**
1. MemTable 暴露近期 OOO 比率或累计计数可供 Engine 决策
2. 可配置阈值（例如 OOO 比率或绝对计数）触发 shard/engine 侧更频繁 flush
3. metrics 可观测（已有 counters 可扩展 gauge/ratio）
4. 单测：构造乱序写入触发 flush 或降载路径
5. 有序主路径性能无显著劣化

---

### EARS-D1-03 超大文件继续拆分

**EARS：**  
当开发者修改热路径生产代码时，相关文件应逐步收敛到 AGENTS 文件 ≤300 行门禁附近；本轮至少再降低 2–3 个最大文件的行数并保持行为不变。

**当前超标样本（约）：**

**验收：** 行为不变；相关包测试/race 通过；文档更新拆分结果。

## 3. D2：中期深化

### EARS-D2-01 可校准查询代价
**EARS：** 当 `QueryWithExplain` 返回 cost 时，`EstimatedSamples` 应与真实扫描潜力相关（part 时间范围、series/字段基数统计），而非仅 series×fields×shards×时间窗启发式。

### EARS-D2-02 SSTable 模块化 + fuzz
**EARS：** 读路径 decode/index/page CRC/解压应可独立测试；关键 block 编解码具备 fuzz 或等价稳健性测试。

### EARS-D2-03 维护 IO 配额
**EARS：** compact 与 downsample 应共享可配置的维护并发/IO 配额，避免饿死前台写查询。

### EARS-D2-04 协议 handler 共享
**EARS：** 同一 operation 的鉴权+业务核心应尽量在 runtime 层共享，HTTP/gRPC 仅做编解码薄封装。

---

## 4. D3：工程化与运维

### EARS-D3-01 Nightly 门禁
**EARS：** 影响存储/查询热路径的合并后，Nightly 应至少跑 fault matrix、soak、选定 scale 与 bench regression。

### EARS-D3-02 版本与兼容矩阵
**EARS：** 发布文档应包含 API semver、format_id、最低可读版本；CHANGELOG 从 Unreleased 演进到可发布说明。

### EARS-D3-03 删除回收 SLA
**EARS：** tombstone 删除后，compaction 物理回收应可观测（队列、耗时、回收字节），并有文档化期望。

### EARS-D3-04 无限扫描策略与告警
**EARS：** 生产配置模板应说明默认 budget/limit 策略，并给出关键 metrics 告警建议。
