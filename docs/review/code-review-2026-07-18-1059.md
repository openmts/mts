## 2. EARS 明细

### EARS-PERF-P0-01 写路径 MemTable 估算 / append / reserve 减负

**状态：已处理**

**EARS**

1. 当系统在写路径更新 MemTable 占用时，系统应当使用 **O(1) 增量计数**（`approxBytes` / `memBytes`），不得在 `ApplyBatch` 热路径对全表做 `approxTableDataBytes` 全扫描。
2. 当 batch 已对列执行 `reserve(n)` 预增长时，系统应当在 `appendSample` 走 **已有容量快路径**，避免重复 `capacityBytes()` 全字段扫描。
3. 当判断是否跳过 batch reserve（唯一 series 前缀）时，系统应当使用 **线性** 去重检测，避免 O(n²) 前缀扫描。
4. 当 `ApproxMemoryBytes` / 内存软限 / flush 决策读取占用时，系统应当返回与增量计数一致的值；全量 `approxTableDataBytes` 仅用于测试校验。

**现状锚点**

- `internal/memtable/memtable.go`：`approxBytes` 增量已存在；`reserveBatchLocked` / `appendSample` 仍有重复容量核算
- `internal/memtable/column_buffer.go`：`appendSample` 每次 `reserve(1)` + 多段 `cap` 计算
- 历史 pprof：`approxTableDataBytes` 曾为写热点；需防回归

**实现要点**

- `appendSample`：`cap` 足够时跳过 `reserve`
- `hasUniqueSeriesPrefix` / typed 变体改为 map 或单遍 set（控制小 batch 分配）
- 补充：大 batch 下 `ApproxMemoryBytes` 调用次数 / 全扫描 hook 为 0 的回归测试

**验收标准**

- [x] 单测：增量估算与全量 `approxTableDataBytes` 在 apply/reserve/snapshot/restore 后一致
- [x] 单测：预 reserve 后 append 不触发全扫描 hook；`hasUniqueSeriesPrefix` 行为不变
- [x] 门禁：`make test` / `make e2e` / lint / race / WriteBatch median 不劣化 >10%

**超时预算**：实现 45–90m；单测 3m；全量验证 20–40m

### EARS-PERF-P0-02 catalog resolve + 列式 WAL 编码批复用

**状态：已处理**

**EARS**

1. 当 `Catalog.ResolvePoints` / `ResolveTypedBatchColumns` 处理同批重复 measurement/tags 时，系统应当复用批内 series/field 解析缓存（已有则巩固），避免每点重复建 key。
2. 当 `wal.Log.Append` / `AppendTyped` 编码列式 payload 时，系统应当优先复用 `encodeScratch` / `frameScratch`，并对 **identity ref 索引、schema 临时结构** 做可复用缓冲，降低每批固定 alloc。
3. 当 `Engine.Write` 规范化输入点时，系统应当尽量减少必经路径上的额外大切片分配（在不破坏调用方输入语义前提下）。
4. 当编码失败时，系统应当不污染可复用 scratch 的可观测语义（错误可诊断，不静默截断有效 WAL）。

**现状锚点**

- `internal/catalog/catalog.go`：`ResolvePoints` 已有 `resolvedFieldArena` + `resolveBatchCache`
- `internal/wal/wal.go`：`encodeScratch` / `frameScratch` 已复用 payload 字节
- `internal/wal/encoding.go`：`batchIdentities` 每批 `make` dense/map/refs
- `internal/engine/engine.go`：`Write` 每批 `make([]Point)` 规范化拷贝

**实现要点**

- WAL：`seriesRefIndex` dense 缓冲复用；`identityRefs` 切片复用（挂在 `Log` 或 encode 上下文）
- schema 构建减少中间 `order` 重复分配
- 保持 formatID=2 字节布局不变（本项不改盘上 WAL 格式，只改 CPU/alloc）

**验收标准**

- [x] 单测：`encodeBatchInto` 复用 destination；identity 去重语义不变
- [x] 单测：catalog 批内重复 series 解析正确；基数拒绝语义不变
- [x] bench：WriteBatch 10k median 相对 baseline +3.50%（<10%）
- [x] 门禁全套通过

**超时预算**：实现 60–120m；验证 20–40m

### EARS-PERF-P0-03 读路径 part 打开减 Stat / 深校验放大

**状态：已处理**

**EARS**

1. 当写入 SSTable part 完成时，系统应当将 **组件文件 size** 写入 part metadata（最终目标格式），使打开路径可不再对每个组件路径做 `storagefs.Stat`。
2. 当 `OpenPartTrusted`（flush/compact 自产 part）打开时，系统应当使用元数据内 size + 边界校验，避免深读全量 index 做 CRC 级遍历。
3. 当 `OpenPart`（恢复/外部校验）打开时，系统仍应保证损坏可拒绝；允许深校验，但应优先使用已打开 fd 的 `Stat` 与元数据 size 交叉验证，避免重复路径 Stat。
4. 当查询扫描已加载 shard 时，系统应当继续复用 `Shard.parts` 常驻 `partReader`，不得按列/按查询重复 `OpenPart`。
5. 当元数据缺少 size（仅测试构造的残缺 fixture）时，系统可回退 Stat；生产新写 part **必须**带 size。

**现状锚点**

- `internal/sstable/read.go`：`loadPartComponentSizes` 对组件 Stat
- `internal/sstable/validate.go`：`validateOpenedPart` 深路径读全 index
- `internal/engine/shard.go`：查询用 `s.parts`；恢复用 `OpenPart`
- 历史 pprof：读/打开路径 `stat` 占比高

**实现要点（POC 直接最终格式）**

- metadata flags 增加 `component_sizes`；`encodeMetadata`/`decodeMetadata` 读写 sizes
- `writePartIndexes` / close writer 时填充 sizes
- `openPart` 优先 metadata sizes；Trusted 保持浅校验
- 回归：损坏 part 仍拒绝；新 part round-trip sizes

**验收标准**

- [x] 新写 part metadata 含组件 size；`OpenPartTrusted` 使用元数据 size
- [x] 损坏/缺失组件在 `OpenPart` 深校验下仍失败
- [x] 查询路径继续复用 `Shard.parts`
- [x] 门禁全套通过；`TestWritePartEmbedsComponentSizes` 覆盖

**超时预算**：实现 90–150m；验证 20–40m

### EARS-PERF-P1-01 跨 shard 并行 ingest 硬化

**状态：已处理**

**EARS**

1. 当一次 `Write`/`WriteTypedBatch` 跨越多个 shard 时，系统应当在 **释放全局 `Engine.mu` 后** 对 shard 批并行落 WAL+MemTable（已有 `writeShardBatches` 则巩固）。
2. 当并行写与 flush/compact 并发时，系统应当保证每 shard 生命周期互斥正确，不出现 MemTable snapshot 与 Apply 竞态。
3. 当并行写部分 shard 失败时，系统应当返回可诊断错误，且已成功 shard 的 WAL 持久语义与现有原子性文档一致（WAL durable 不回滚）。
4. 当启用并行写时，系统应当暴露必要指标/日志字段（并行 batch 数、失败 shard），便于与竞品多核写对照调优。

**验收标准**

- [x] 多 shard 写正确性单测 + race
- [x] 并行错误 `errors.Join` + shard 标识；ingest 指标可观测
- [x] 门禁全套；WriteBatch median 记录于验证表

**超时预算**：实现 2–4h；验证 30–60m

### EARS-PERF-P1-02 顺序 float 列式编码 / 压缩特化

**状态：已处理**

**EARS**

1. 当字段为 `float64` 且时间戳近似单调时，系统应当优先走专用时间戳 delta + 浮点有效编码路径，减少通用分支。
2. 当压缩开启时，系统应当对顺序数值块选择更合适的默认算法/级别（可配置），并在 stats 中暴露压缩比。
3. 当解码扫描时，系统应当尽量避免 interface/`FieldValue` 装箱的热路径（列式直接输出）。

**验收标准**

- [x] 默认编码策略归一化（timestamp/float/int/string）；显式 plain 保留
- [x] float XOR 优先路径；既有压缩 round-trip 回归覆盖
- [x] 门禁全套

**超时预算**：实现 4–8h；验证 40–80m

### EARS-PERF-P2-01 查询向量化 / block skip / 流式

**状态：已处理（阶段性）**

**EARS**

1. 当查询带时间窗与 field 投影时，系统应当在 page/block 级跳过不重叠块，并在 explain 中体现跳过统计。
2. 当结果集超过保护阈值时，系统应当流式返回（iterator），默认保护仍生效。
3. 当执行聚合时，系统应当减少中间 `[]Sample` 物化，优先列批累加。

**验收标准**

- [x] `QueryExplain` 暴露 index/page skip 统计并同步 pushdown 标记
- [x] iterator/e2e 既有路径保持通过（本轮未改 streaming 契约）
- [x] 门禁全套；深度向量化聚合留待后续

**超时预算**：实现 1–2d；验证 1h+

## 6. Wide Batch 写路径 pprof 再压（2026-07-18）

### 采集
- `BenchmarkEngineWriteWideBatch/points=10000` + CPU/mem pprof
- 优化前 median ≈ **49.3ms/op**，~50.6MB/op，~148.6k allocs/op

### 热点
1. `toModelPoints` / 字段 map 转换与 tags clone
2. `Catalog.ResolvePoints` / `resolveFieldsFromSchema`
3. WAL `lookupPointField` 宽表 O(rows×fields²) 查找
4. GC `scanObject`（分配压力次生）

### 改动
- public 默认纳秒精度批转换快路径
- catalog 同构 batch 字段模板复用 + schema 单趟校验后填充
- 列式 WAL dense 宽表按 schema 顺序直接写值列

### 结果
| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| WideBatch 10k ns/op（pprof 会话） | 49.3ms | 47.1ms | **-4.56%** |
| WideBatch 10k vs 仓库 baseline | — | — | **+1.51%**（仍 <10%） |
| WriteBatch 10k vs baseline | — | — | **-2.06%** |
| Wide B/op vs baseline | — | — | **-3.14%** |

说明：allocs/op 基本持平（仍受 point/fields map 模型约束）；CPU 热点中 `lookupPointField` 已从 flat top 显著下降。
