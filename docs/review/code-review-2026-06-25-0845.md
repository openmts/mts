# MTS 对外 API 完整性检视报告

## 结论

当前 `mts-server` 对外 API 不完整。项目根包 `github.com/openmts/mts` 已经具备写入、查询、元数据、用户与 DB 级权限、维护、健康状态、降采样等能力，但 `cmd/mts-server` 目前只暴露了健康检查、点写入、行式查询、flush 和 compact。

因此，如果要把 `mts-server` 作为外部用户可商用访问入口，需要先定义稳定 HTTP/gRPC 协议边界，再按数据面、管理面、用户权限面、元数据面、配置面、观测面拆分补齐接口。

## 检视范围

- `engine.go`：根包 `Engine` 已公开能力。
- `values.go`、`query_types.go`、`result_types.go`：写入、查询与返回模型。
- `user_types.go`、`local_user_manager.go`：用户与 DB 级权限模型。
- `downsample.go`、`downsample_types.go`：降采样管理与执行能力。
- `cmd/mts-server/http.go`、`cmd/mts-server/grpc.go`、`cmd/mts-server/runtime.go`、`cmd/mts-server/config.go`：当前服务入口。
- `internal/queryservice/*`：内部查询服务能力。
- `internal/service/*`：内部运维 HTTP 能力。
- `cmd/mts-storage/main.go`、`internal/storagecheck/*`：本地存储诊断、修复、迁移、快照与恢复能力。
- `README.md`：当前稳定 API 边界说明。

## 当前 `mts-server` 已暴露接口

HTTP：

- `GET /healthz`
- `GET /readyz`
- `POST /api/v1/data/write`
- `POST /api/v1/data/query/rows`
- `POST /api/v1/admin/flush`
- `POST /api/v1/admin/compact`

gRPC：

- `mts.v1.MTSServer/Health`
- `mts.v1.MTSServer/Write`
- `mts.v1.MTSServer/QueryRows`
- `mts.v1.MTSServer/Flush`
- `mts.v1.MTSServer/Compact`

当前缺口：

- 没有用户 CRUD 和 DB 级权限管理接口。
- 没有列式查询、Explain、查询统计、流式查询接口。
- 没有 typed batch 写入接口。
- 没有 database、retention policy、measurement、field、series 元数据接口。
- 没有配置查询接口。
- 没有 metrics、query stats、compaction stats、storage memory、maintenance errors 等观测接口。
- 没有降采样策略管理与手动执行接口。
- 没有统一错误码、认证鉴权、OpenAPI/protobuf 契约和版本兼容说明。

## 建议命名空间

建议继续沿用当前数据面与管理面拆分，并补充用户权限面：

- 数据面：`/api/v1/data/*`，处理写入、查询和只读数据目录发现能力。
- 管理面：`/api/v1/admin/*`，处理 database、retention、维护、配置、降采样和运行状态。
- 用户权限面：`/api/v1/users/*` 和 `/api/v1/authz/*`，处理用户与授权数据。
- 观测面：保留标准 `/healthz`、`/readyz`、`/metrics`，复杂运行状态放入 `/api/v1/admin/stats/*`。
- gRPC：建议拆成 `mts.v1.DataService`、`mts.v1.AdminService`、`mts.v1.UserService`、`mts.v1.MetaService`、`mts.v1.ConfigService`，避免把所有 RPC 堆在一个 `MTSServer` 服务里。

## P0：建议作为商用外部 API 首批补齐

### 1. 数据写入接口

现有根包能力：

- `Engine.Write(ctx, []Point, WriteOptions)`
- `Engine.WriteTypedBatch(ctx, TypedBatch, WriteOptions)`

建议 HTTP：

- `POST /api/v1/data/write`：保留当前点写入接口。
- `POST /api/v1/data/write/typed`：新增 typed batch 写入接口，适合高吞吐写入和减少 JSON 重复字段。

建议 gRPC：

- `DataService.Write`
- `DataService.WriteTypedBatch`

注意事项：

- 请求必须支持 `precision`，与 `Point.Precision`、`TypedBatch.Precision` 对齐。
- 写入错误应区分请求格式错误、schema 冲突、权限不足、存储错误。

### 2. 数据查询接口

现有根包能力：

- `Engine.QueryRows(ctx, Query)`
- `Engine.QueryColumns(ctx, Query)`
- `Engine.QueryRowIterator(ctx, Query)`
- `Engine.QueryColumnIterator(ctx, Query)`
- `Engine.QueryWithExplain(ctx, Query)`
- `Engine.QueryStatsSnapshot()`

建议 HTTP：

- `POST /api/v1/data/query/rows`：保留当前行式查询。
- `POST /api/v1/data/query/columns`：新增列式查询。
- `POST /api/v1/data/query/explain`：返回结果、Explain、Stats。
- `POST /api/v1/data/query/stream`：返回 NDJSON 流式结果，避免大结果一次性 materialize。
- `GET /api/v1/data/query/stats`：查询服务级统计。

建议 gRPC：

- `DataService.QueryRows`
- `DataService.QueryColumns`
- `DataService.QueryWithExplain`
- `DataService.QueryStream`，使用 server streaming。
- `DataService.QueryStats`

注意事项：

- 查询入口仍使用结构化 `Query`，不引入 SQL、InfluxQL、PromQL parser。
- 大结果查询应优先引导用户使用 stream/cursor，而不是 `rows` 一次性返回。
- 查询请求必须支持返回时间戳 `precision`。
- 可以复用 `internal/queryservice` 的 admission、timeout、audit、cache、stream 思路，但不能原样暴露 `/query` 这类 internal 路径。

### 3. 用户系统与 DB 级权限接口

现有根包能力：

- `Engine.CreateUser`
- `Engine.UpdateUser`
- `Engine.GetUser`
- `Engine.ListUsers`
- `Engine.DeleteUser`
- `Engine.GrantDatabasePermission`
- `Engine.RevokeDatabasePermission`
- `Engine.ListDatabasePermissions`
- `Engine.CheckUserDatabasePermission`

建议 HTTP：

- `POST /api/v1/users`：创建用户。
- `GET /api/v1/users`：列出用户。
- `GET /api/v1/users/{name}`：查询用户。
- `PUT /api/v1/users/{name}`：更新用户显示名、禁用状态和 metadata。
- `DELETE /api/v1/users/{name}`：删除用户及权限。
- `GET /api/v1/users/{name}/database-permissions`：列出用户 DB 权限。
- `PUT /api/v1/users/{name}/database-permissions/{database}/{permission}`：授予 DB 权限。
- `DELETE /api/v1/users/{name}/database-permissions/{database}/{permission}`：撤销 DB 权限。
- `POST /api/v1/authz/database/check`：检查某用户是否具备某 database 权限。

建议 gRPC：

- `UserService.CreateUser`
- `UserService.UpdateUser`
- `UserService.GetUser`
- `UserService.ListUsers`
- `UserService.DeleteUser`
- `UserService.GrantDatabasePermission`
- `UserService.RevokeDatabasePermission`
- `UserService.ListDatabasePermissions`
- `UserService.CheckDatabasePermission`

注意事项：

- 当前用户模块是身份与授权数据管理，不包含密码、登录、token 签发、session。
- 对外 server 如果开放用户接口，必须同时设计请求认证，否则用户管理接口本身会成为高危入口。
- 第三方权限系统对接边界应继续保持 `UserManager` 接口化。

### 4. 元数据接口

现有根包能力：

- `Engine.CreateDatabase`
- `Engine.DropDatabase`
- `Engine.CreateRetentionPolicy`
- `Engine.ListRetentionPolicies`
- `Engine.ListMeasurements`
- `Engine.ListFields`
- `Engine.ListSeries`

建议 HTTP：

- `POST /api/v1/admin/databases`：创建 database。
- `DELETE /api/v1/admin/databases/{database}`：删除 database。
- `POST /api/v1/admin/databases/{database}/retention-policies`：创建或更新 retention policy。
- `GET /api/v1/admin/databases/{database}/retention-policies`：列出 retention policy。
- `GET /api/v1/data/databases/{database}/measurements`：列出 measurement。
- `GET /api/v1/data/databases/{database}/measurements/{measurement}/fields`：列出字段 schema。
- `GET /api/v1/data/databases/{database}/measurements/{measurement}/series`：按 tags 过滤列出 series。

建议 gRPC：

- `MetaService.CreateDatabase`
- `MetaService.DropDatabase`
- `MetaService.CreateRetentionPolicy`
- `MetaService.ListRetentionPolicies`
- `MetaService.ListMeasurements`
- `MetaService.ListFields`
- `MetaService.ListSeries`

注意事项：

- 创建、删除 database 属于管理面，需要 admin 权限。
- measurement、field、series 发现能力更贴近数据面读能力，需要 read 权限。

### 5. 配置查询接口

现有能力：

- `cmd/mts-server/config.go` 已有 YAML 配置模型。
- 根包 `Options`、`DefaultOptions`、`Validate` 已定义 Engine 生效选项。

建议 HTTP：

- `GET /api/v1/admin/config`：返回启动配置，敏感字段脱敏。
- `GET /api/v1/admin/config/effective`：返回合并默认值后的生效配置。
- `GET /api/v1/admin/config/schema`：返回配置字段说明，便于外部控制台生成表单。

建议 gRPC：

- `ConfigService.GetConfig`
- `ConfigService.GetEffectiveConfig`
- `ConfigService.GetConfigSchema`

注意事项：

- 首阶段建议只读，不建议实现运行时修改配置。
- 若后续支持动态配置，需要明确哪些字段可热更新、哪些必须重启。

### 6. 基础维护与运行状态接口

现有根包能力：

- `Engine.Flush`
- `Engine.Compact`
- `Engine.CompactWithResult`
- `Engine.ApplyRetention`
- `Engine.MaintenanceErrors`
- `Engine.StorageMemorySnapshot`
- `Engine.CompactionStatsSnapshot`
- `Engine.HealthSnapshot`

建议 HTTP：

- `POST /api/v1/admin/flush`：保留。
- `POST /api/v1/admin/compact`：保留，并统一返回 compaction result。
- `POST /api/v1/admin/retention/apply`：手动触发 retention。
- `GET /api/v1/admin/maintenance/errors`：读取后台维护错误。
- `GET /api/v1/admin/stats/storage-memory`：读取存储内存快照。
- `GET /api/v1/admin/stats/compaction`：读取 compaction 统计。
- `GET /api/v1/admin/health`：返回完整 `HealthSnapshot`。
- `GET /metrics`：Prometheus 文本指标。

建议 gRPC：

- `AdminService.Flush`
- `AdminService.Compact`
- `AdminService.ApplyRetention`
- `AdminService.ListMaintenanceErrors`
- `AdminService.GetStorageMemorySnapshot`
- `AdminService.GetCompactionStats`
- `AdminService.GetHealth`
- `AdminService.GetMetrics`，如需要也可只保留 HTTP `/metrics`。

注意事项：

- `internal/service` 已有 `/metrics`、`/healthz`、`/readyz`、`/admin/compact`、pprof，可迁移到 `mts-server` 命名空间和认证体系下。
- 管理接口必须具备 admin 级鉴权和审计。

- 配置项明确声明风险。

## P2：可以提供，但不建议默认作为远程外部 API

### 1. 存储诊断、修复、迁移、快照与恢复

现有本地 CLI 能力：

- `mts-storage check`
- `mts-storage repair`
- `mts-storage migrate`
- `mts-storage snapshot`
- `mts-storage restore`

底层内部能力：

- `storagecheck.Check`
- `storagecheck.Repair`
- `storagecheck.Migrate`
- `storagecheck.Snapshot`
- `storagecheck.Restore`

建议处理方式：

- 首选继续作为本地 CLI 能力提供，不纳入默认远程 API。
- 如确实需要远程调用，只建议提供 admin-only、本地绑定、默认 dry-run 的接口。

可选 HTTP：

- `POST /api/v1/admin/storage/check`
- `POST /api/v1/admin/storage/repair-plan`
- `POST /api/v1/admin/storage/repair-apply`
- `POST /api/v1/admin/storage/snapshot`
- `POST /api/v1/admin/storage/restore`
- `POST /api/v1/admin/storage/migrate-plan`
- `POST /api/v1/admin/storage/migrate-apply`

风险：

- 这类接口能直接修改或复制本地数据目录，远程暴露会显著增加误操作和安全风险。
- `restore`、`migrate apply` 应要求服务停止或进入维护模式，否则可能与写入、flush、compaction 并发冲突。

## 需要统一设计的横切能力

### 1. 外部协议契约

- HTTP 需要 OpenAPI 3.x 文档。
- gRPC 需要 protobuf，而不是长期依赖手写 JSON codec 的动态 `ServiceDesc`。
- 错误响应需要统一字段：`ok`、`code`、`message`、`details`、`request_id`。
- API 需要版本兼容策略，例如 `/api/v1` 和 `mts.v1` 的破坏性变更规则。

### 2. 认证与鉴权

- 至少需要 admin token 或 API key 机制保护管理面。
- 数据写入需要 write 权限，数据查询和元数据发现需要 read 权限，database/retention/downsample/maintenance 需要 admin 权限。
- 用户接口本身必须要求 admin 权限。
- 应把当前 `UserManager` 纳入 HTTP/gRPC 请求鉴权链路。

### 3. 请求限制与安全

- 写入 body 大小限制。
- 查询 timeout、limit、budget、并发 admission。
- 流式查询的连接生命周期管理。
- 管理操作审计日志。
- pprof、storage repair、restore 默认关闭。

### 4. 可观测性

- 统一 `/metrics`。
- 查询统计、compaction 统计、storage memory、maintenance errors 应可查询。
- 管理操作和用户权限变更应写审计。

### 5. 文档与用例

- README 只保留简洁入口，详细 API 文档放入 `docs/api/`。
- 增加 OpenAPI、protobuf、curl 示例和 grpcurl 示例。
- 每个对外接口必须有 HTTP 和 gRPC 端到端测试。

## 推荐实施顺序

1. 冻结 API 命名空间和错误模型：先确定 HTTP/gRPC 服务拆分、请求响应格式、认证鉴权策略。
2. 补 P0 数据面：typed write、columns query、explain、stream、query stats。
3. 补 P0 用户权限面：用户 CRUD、DB 权限 CRUD、权限检查，并接入鉴权中间件。
4. 补 P0 元数据与配置只读接口：database、retention、measurement、field、series、effective config。
5. 补 P0 管理与观测接口：metrics、maintenance errors、storage memory、compaction stats、retention apply。
6. 补 P1 降采样和 query governance 接口。
7. 最后再评估 P2 storage ops 是否开放远程入口；默认保留 CLI-first。

## 待用户决策项

- 是否把 `mts-server` 定义为正式商用外部 API 入口，而不仅是开发/验证入口。
- 是否要求 HTTP 与 gRPC 完全等价，还是 gRPC 只覆盖数据面高频接口。
- 是否首批就加入认证鉴权；若开放用户接口和管理接口，建议必须加入。
- 是否首批实现降采样接口，还是先只保留 Go API。
- 是否禁止远程 storage repair/restore/migrate，只保留本地 `mts-storage` CLI。
- 配置接口是否只读；建议首批只读。
