## 1. 结论摘要

当前 MTS 已经具备可运行的单机时序存储主链路：

- 写入：Point / TypedBatch → Catalog resolve → WAL → MemTable → Flush → Manifest/SSTable
- 查询：Builder/API → 引擎侧 `BuildQueryPlan` → MemTable+SSTable 扫描 → `queryexec` 过滤/聚合/分页/预算
- 运维：compaction、retention、downsample、recovery audit、`mts-storage check/repair`、metrics 文档
- 服务：`mts-server` HTTP/gRPC、本地用户权限、runtime facade

**总体判断**：功能面已经接近“单机商用雏形”，主要风险不再是“能不能写读”，而是：

1. **正确性边界仍有若干状态机缺口**（flush/checkpoint 失败回滚、查询与生命周期并发、retention 粒度）
2. **写入与维护被全局锁串行化**，吞吐与延迟上限明显
3. **查询架构存在双栈**（引擎热路径 vs `queryservice` 分层计划器），维护成本与语义一致性风险高
4. **模块体积与职责仍偏重**，与仓库 AGENTS 的硬约束（文件 ≤300 行、函数 ≤50 行）差距大
5. **高基数与长周期运维能力**（catalog 膨胀、细粒度删除、分片内 retention、SLO/压测门禁）尚未闭环

本次按 EARS（Easy Approach to Requirements Syntax）把改进点写成可验收需求清单，并标注优先级与证据位置。

## 4. P0：正确性与数据安全（必须优先）

### EARS-P0-01 Flush Checkpoint 失败双写态

**EARS：**  
当系统在 Manifest 已成功提交新 part 之后、WAL Checkpoint 失败时，引擎应当保证数据只在一个权威位置可读，且不得同时把 snapshot 回灌 MemTable 并保留已提交 part。

**现状证据：**

- `internal/engine/shard.go` `flushLocked`：Manifest 写入成功后 `s.parts`/`s.manifest` 已更新；若 `wal.Checkpoint()` 失败则 `s.mem.Restore(snapshot)` 并返回错误。
- 结果：同一批数据同时存在于 SSTable part 与 MemTable（且 WAL 未截断）。
- 查询侧通过 `WriteSeq` 去重可能“读正确”，但内存/磁盘放大、后续 flush/compaction 语义复杂，故障注入后行为不直观。

**影响：**

- 进程内内存暴涨、重复 flush、维护路径难推理
- 运维看到 Flush 失败时，实际数据可能已经 durable 在 part 中

**建议修复：**

1. 定义 flush 提交阶段机：`part_written → manifest_committed → wal_checkpointed → mem_released`
2. Manifest 提交成功后，Checkpoint 失败应：
   - **不** Restore 已提交 snapshot 到 mem
   - 记录 maintenance/recovery issue
   - 允许下次启动按“manifest 已有 + WAL 重复 replay + WriteSeq 去重”恢复
3. 增加故障注入测试：`afterManifestBeforeWALTrunc` 失败后查询结果不翻倍、内存不双计

**验收标准：**

- 故障注入后 `QueryRows` sample 数 = 逻辑写入数
- MemTable sample 不包含已 commit part 中的同一 WriteSeq 集合
- 重启后数据完整且无重复放大

### EARS-P0-02 查询迭代器与 Shard 生命周期安全

**EARS：**  
当查询 iterator 仍在使用时，如果发生 `DropDatabase` / retention 删除 / `Close`，系统应当安全阻塞、返回明确错误或保证 iterator 读到一致快照，而不是访问已关闭资源导致未定义行为。

**现状证据：**

- `queryShardsWithCandidates` 在 `e.mu` 下复制 `[]*Shard` 指针后立即解锁
- `ScanColumns` 持有 `lifecycleMu.RLock` 贯穿流式读取
- `DropDatabase` / `ApplyRetention` 在 `e.mu` 下 `Close` 并 `delete(e.shards, id)`，`Close` 需 `lifecycleMu.Lock`
- 并发上通常会“等 RLock 释放”，但：
  - 长查询会阻塞删除/关闭
  - 关闭后 iterator 后续 Next/Close 语义、错误类型未产品化
  - 若未来改为 try-lock 或缩短 RLock 范围，极易引入 use-after-close

**建议修复：**

1. 为 Shard 引入 `epoch` / `refCount` / `generation`
2. 查询开始时 `AcquireRead(shard)`，结束时 `Release`
3. Drop/Close 等待 ref=0 或强制取消查询 context
4. 对外统一错误：`ErrEngineClosed` / `ErrShardRemoved`

**验收标准：**

- 并发压测：持续 QueryRowIterator + 周期性 DropDatabase，无 panic、无挂死
- iterator 在资源回收后返回可识别错误

### EARS-P0-03 WAL 成功 / MemTable 失败的可见性契约

**EARS：**  
当 WAL append 成功但 MemTable apply 失败时，系统应当要么原子回滚 WAL，要么在错误返回的同时保证后续查询/重启仍能读到该批数据，并对外明确契约。

**现状证据：**

- `Shard.WriteBatch`：先 `wal.Append`，再 `mem.ApplyBatch`
- 失败时直接返回，无补偿
- 当前 MemTable apply 多数路径几乎不失败，但接口返回 `error`，未来扩展/注入后会踩坑

**建议修复：**

1. 短期：文档化“WAL 已提交即 durable；查询可见性以 mem+sst 为准；进程内失败需重启恢复”
2. 中期：mem apply 失败时将记录记入“pending replay buffer”或触发受控 panic/只读降级
3. 长期：单线程 apply 管道保证 WAL 与 mem 顺序一致提交

**验收标准：**

- 故障注入 mem apply 错误后，要么调用方重试可幂等成功，要么重启后数据可见
- 不存在“返回错误且重启后数据丢失”

---

### EARS-P0-04 Shard 级写入与维护互斥语义统一

**EARS：**  
当写入、flush、compaction、scan 并发发生时，系统应当在 Shard 级有清晰锁层级与不变式，避免“Engine 全局锁掩盖 Shard 级竞态”。

**现状证据：**

- 写入主路径持有 `Engine.mu`，再调用 `Shard.WriteBatch`（**不**取 `lifecycleMu`）
- `Flush/Compact` 取 `lifecycleMu.Lock`
- `ScanColumns` 取 `lifecycleMu.RLock`
- 目前靠 `Engine.mu` 把写与 compact 串起来，scan 靠 mem 自己的锁 + parts 的 RLock
- 一旦后续做“释放全局锁、按 shard 并行写”，当前 `WriteBatch` 不持 `lifecycleMu` 会与 flush 的 `SnapshotAndReset` 竞态

**建议修复：**

1. 明确锁层级：`Engine.mu`（仅 shard map/元数据） < `Shard.lifecycleMu` < `mem.mu` / `wal.mu`
2. `WriteBatch` 至少在 flush 触发段与 mem snapshot 段持有正确互斥
3. 增加 `-race` 并发测试：多 goroutine 写 + 后台 compact + 流式查询

**验收标准：**

- 去掉“写路径长期持有 Engine.mu”后，race 测试通过
- 不出现 mem snapshot 丢点或 part 列表撕裂

## 5. P1：结构、性能与产品化关键缺口

### EARS-P1-01 全局写锁限制吞吐

**EARS：**  
当多个 shard 同时写入时，系统应当允许跨 shard 并行 append，而不是用单个 `Engine.mu` 串行化全部写路径。

**现状证据：**

- `writeResolved` / `writeResolvedTyped` 全流程 `e.mu.Lock`
- 内存限额、分 shard、写 seq 分配都在同一把锁内
- 后台 compact 也抢同一把锁

**TSDB 视角：**

- 成熟单机引擎通常：全局只保护元数据/序列号；WAL/MemTable 按 shard（或 partition）并行
- 当前模型在多 measurement / 多时间分片场景会过早触达吞吐天花板

**建议：**

1. `writeSeq` 改为 atomic 或分 shard 序列 + 全局合并规则
2. 内存预算用分层限额（全局 soft/hard + per-shard）
3. `groupByShard` 后对各 shard `errgroup` 并行写
4. 保留全局 hard limit 的快速拒绝路径

**验收标准：**

- 多 shard 并发写吞吐接近线性扩展（至少 4 shard 下 ≥ 2.5x 单 shard）
- p99 写延迟不因无关 shard flush 抖动失控

---

### EARS-P1-02 查询双栈收敛

**EARS：**  
当执行 public/storage 查询时，系统应当只通过一套权威计划与执行语义产出结果；分层计划器若保留，必须成为主路径或降为实验特性。

**现状证据：**

- 热路径：`internal/engine/query_plan.go` + `query.go` + `queryexec`
- 旁路：`querylang → analyzer → planner → optimizer → physical → queryservice.LayeredExecutor`
- `internal/engine` 对 layered 栈几乎无生产依赖（`querylang` 仅 query_spec 相关）
- 双栈导致过滤下推、聚合语义、explain/profile 字段可能漂移

**建议：**

1. 选定权威栈：
   - 方案 A：继续以 engine+queryexec 为权威，layered 仅服务 HTTP 兼容并加“非权威”标注
   - 方案 B：把 layered 下沉为 engine 主路径，删除重复 `BuildQueryPlan` 逻辑
2. 建立同一批 golden query 双向对比测试
3. 在 README/llms.txt 明确“当前权威查询入口”

**验收标准：**

- 同一 `model.Query` 在两条路径结果一致（排序、空值、聚合边界）
- 删除或隔离未使用计划层代码，降低双维护成本

---

### EARS-P1-03 Retention 粒度不足

**EARS：**  
当配置了数据保留期 `Retention` 时，系统应当删除所有时间戳早于 cutoff 的数据，而不仅是“整 shard 结束时间早于 cutoff”的 shard。

**现状证据：**

- `ApplyRetention` 仅在 `shard.opts.End < cutoff` 时删整个 shard
- 默认 `ShardDuration=1h` 时，当前小时内的过期点不会被清理
- 对更长 shard duration 更危险

**建议：**

1. 分片级删除保留
2. 分片内：tombstone 时间范围 + compaction 时物理清除
3. 或强制要求 `ShardDuration` 与 retention 对齐并在 Validate 中约束

**验收标准：**

- 写入跨多个小时数据后，将 now 推进到 retention 外，查询不再返回过期点
- 磁盘占用在 compaction 后下降

---

### EARS-P1-04 删除能力产品化

**EARS：**  
当用户需要删除时间范围或 series 数据时，public API 应当提供稳定删除接口，并保证 WAL/tombstone/compaction 完整链路可测。

**现状证据：**

- Shard 有 `DeleteRange` + tombstone WAL record
- 根包 public API 未见对等删除入口（以用户/元数据删除为主）
- 删除后的读可见性、与 downsample/retention 交互需要更明确契约

**建议：**

- public：`Delete(ctx, DeleteRequest{DB, RP, Measurement, Tags, Start, End})`
- 语义：先写 tombstone，查询过滤，compact 时 drop
- 明确是否支持“立即回收磁盘”

---

### EARS-P1-05 Catalog 高基数治理

**EARS：**  
当 series/tag/field 基数超过配置阈值时，系统应当拒绝或降级新 series 创建，并暴露可观测指标，而不是无限膨胀内存 map。

**现状证据：**

- `internal/catalog.Catalog` 维护 `seriesByKey`、`seriesByTag`、`series`、`fields` 等全量内存结构
- 有 tag 倒排雏形，但缺少硬上限与驱逐
- TSDB 生产事故最高发之一即 tag 爆炸

**建议：**

1. `MaxSeries` / `MaxFields` / `MaxTagValuesPerKey`
2. 超限返回明确错误（可映射 public `ErrInvalidOptions` 或新 `ErrCardinalityLimit`）
3. metrics：series 总数、创建速率、拒绝次数
4. 可选：measurement 级配额

---

当修改生产代码时，系统代码组织应当满足“文件 ≤300 行、函数 ≤50 行”的工程门禁，或在文档中明确阶段性豁免与拆分计划。

### EARS-P1-07 公共错误契约

**EARS：**  
当 internal 返回业务错误时，public API 应当稳定映射为可 `errors.Is` 的类别，并避免直接泄漏不稳定 internal 错误串作为唯一依据。

**现状证据：**

- `publicError` 仅映射部分 not found / unsupported
- 其它错误原样返回 internal 内容
- 根包同时依赖 `internal/engine`、`queryanalyzer`、`queryexec`、`runtime` 做错误判断

**建议：**

- 收敛错误码枚举（Invalid / NotFound / Conflict / ResourceExhausted / Unavailable / Internal）
- server HTTP/gRPC 统一基于类别映射

---

### EARS-P1-08 后台任务可控性

**EARS：**  
当 compaction/downsample 后台任务运行时，系统应当支持 context 取消、并发上限、积压指标与跳过原因统计，避免与前台写查询饿死。

**现状证据：**

- 后台 compact loop、downsample 100ms tick + per-policy goroutine
- 有 memory soft limit skip 与部分 stats
- 仍缺统一 worker pool、全局 inflight 上限、任务队列深度

**建议：**

- 统一 `maintenanceScheduler`
- metrics：queue depth、running、skip reasons、last success/fail
- downsample 与 compact 共享 IO 带宽配额

## 6. P2：性能、工程化与可维护性

### EARS-P2-01 MemTable 乱序与重复点成本

**EARS：**  
当同一 series 在短时间收到大量乱序/重复时间戳时，系统应当限制内存膨胀并保持可预期的 compact/query 成本。

**现状：**

- MemTable 以 column buffer append 为主，查询时再 sort/dedupe（`WriteSeq` 优先）
- 对乱序友好，但会放大 mem 与 flush CPU

**建议：**

- 热路径假设近似有序，检测无序率
- 无序率超阈值时切换有序插入或更频繁 flush
- 统计 `out_of_order_samples_total`

---

### EARS-P2-02 SSTable 读路径模块化

**EARS：**  
当开发者修改 SSTable 读路径时，应当能在独立包/文件中验证 decode、index probe、page CRC、解压，而不必理解 1000+ 行单体文件。

**建议：** page reader / series index / value decoder / stats 拆分，并补 block 级 fuzz。

---

### EARS-P2-03 查询代价与计划可解释性

**EARS：**  
当 `QueryWithExplain` 返回 cost 时，成本应当与真实扫描量相关，并可被优化器/限流使用。

**现状：** `estimateQueryCost` 以 series×fields×shards 与 limit 为主，plan class 粗粒度。

## 10. 详细 EARS 条目（可直接进 plans）

### 10.1 数据正确性

1. **当** Manifest 提交成功且 WAL checkpoint 失败，**系统应当**把该 part 视为已提交且不得回灌 MemTable。  
2. **当**查询流未关闭，**系统应当**阻止破坏性 Close 完成或取消查询并返回明确错误。  
3. **当**同一 timestamp 多版本写入，**系统应当**按 WriteSeq 选择最新版本且结果稳定。  
4. **当**进程在 flush 的任意阶段崩溃，**系统应当**在重启后恢复到“不丢已确认写、不多出逻辑点”的状态。  
5. **当** tombstone 覆盖某时间范围，**系统应当**在查询结果中排除被删样本，并在后续 compaction 中可物理回收。

### 10.2 写入路径

1. **当**写入批量跨多个 shard，**系统应当**允许并行写各 shard，仅串行化真正共享的元数据更新。  
2. **当**内存 soft limit 触及，**系统应当**优先触发 flush/限流，而不是长时间持锁自旋。  
3. **当** `WriteOptions.Sync=true`，**系统应当**在返回前保证该批 WAL durable。  
4. **当**字段类型冲突，**系统应当**拒绝写入并返回稳定错误类别。  
5. **当** series 基数超限，**系统应当**拒绝创建新 series。

### 10.3 查询路径

1. **如果**查询未设置 limit 且未设置 budget，**则**系统应当使用可配置默认保护或拒绝无限扫描。  
2. **当**聚合查询执行时，**系统应当**在 explain 中标明下推项与 post-filter 项。  
3. **当**同时存在 layered 与 engine 执行器时，**系统应当**提供一致性对比测试或只保留一个权威实现。  
4. **当** context 取消时，**系统应当**及时停止扫描并释放 shard 读锁。  
5. **当**返回 iterator 时，**系统应当**在 Close 时释放全部底层资源（文件句柄、锁、缓冲）。

### 10.4 维护与运维

1. **当** retention 到期，**系统应当**删除所有过期时间戳数据（跨当前分片）。  
2. **当**后台 compact 与前台写冲突，**系统应当**可观测 skip/delay，而不是无界阻塞写。  
3. **当** downsample 失败，**系统应当**记录 watermark 错误信息且支持断点续跑。  
4. **当**磁盘可用空间低于阈值，**系统应当**拒绝会扩大占用的 compact/flush 并告警。  
5. **当**启动发现孤儿 part，**系统应当**按恢复协议清理或报告。

### 10.5 工程与 API

1. **当**新增 public API，**系统应当**提供 example_test 与错误契约测试。  
2. **当**生产文件超过 300 行，**系统应当**在下一轮重构中拆分或登记豁免与截止日期。  
3. **当** CI 运行时，**系统应当**执行 lint、覆盖率与关键包 race。  
4. **当**发布版本时，**系统应当**更新 CHANGELOG 与格式兼容说明。  
5. **如果**功能仅 internal 可用，**则** README 必须明确“非稳定 API”。
