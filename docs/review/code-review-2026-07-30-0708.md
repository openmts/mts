### REV-20260730-P0-03：3 个管理员 gRPC RPC 绕过鉴权

**处理状态：已处理（2026-07-30）。** `operationCatalog` 的 `authAdmin` 现统一接入 gRPC 鉴权拦截器，不再依赖各 handler 手写检查；自动矩阵测试枚举所有管理员 RPC，验证匿名为 `Unauthenticated`、普通用户为 `PermissionDenied`，并保留管理员成功路径。定向测试、协议 E2E、全仓测试、server race 和 `golangci-lint` 均通过。

- 范围：`mts-server`
- 严重度：P0
- 位置：`cmd/mts-server/operation_registry.go:801-833`、`cmd/mts-server/grpc.go:1007-1032`。
- 触发条件：匿名客户端调用 `ListAudit`、`ListStorageSnapshots` 或 `DeleteStorageSnapshot`。
- 根因：Registry 虽把这些操作标记为 `authAdmin`，但通用 `unaryHandler` 不读取 Registry 的鉴权元数据，三个具体 handler 也没有调用 `requireGRPCAdmin`。
- 影响：未认证客户端可读取审计记录、枚举快照路径并删除本地存储快照；HTTP 对应接口有管理员鉴权，形成协议级权限绕过。

EARS 验收：

1. 当匿名或普通用户调用任一管理员 gRPC RPC 时，系统必须返回 `Unauthenticated` 或 `PermissionDenied`。
2. 当管理员凭据有效时，三个 RPC 应保持现有成功行为。
3. Registry 中标记为 `authAdmin` 的所有 gRPC 操作必须通过统一、不可遗漏的鉴权层，而不是依赖每个 handler 手写。
4. 应增加 HTTP/gRPC 权限矩阵测试，防止后续新增操作再次遗漏。

### REV-20260730-P0-04：固定默认管理员自动创建且重启恢复权限

**处理状态：已处理（2026-07-30）。** 服务启动不再创建固定账号，也不会修改已有 `admin` 的角色或禁用状态。首次部署复用已有强随机 `auth.admin_token`，通过受保护且写审计的用户 API 显式创建管理员，无新增配置/schema、无明文秘密日志或落盘。测试覆盖全新目录、禁用管理员和降权管理员重启场景；README、示例配置和生产 runbook 已同步。

- 范围：`mts-server`
- 严重度：P0
- 位置：`cmd/mts-server/runtime.go:92-123`、`README.md:214`。
- 触发条件：密码认证开启后首次启动，或重启一个已禁用/降权的 `admin` 账号。
- 实际行为：服务无条件创建固定 `admin/admin`；若账号存在但被禁用或降权，重启会强制恢复为启用的管理员。

EARS 验收：

2. 当管理员被禁用或降权后重启时，系统必须保留该状态。
3. bootstrap 仅允许一次性、可审计地创建账号，且不得把明文秘密写入日志或版本库。
4. 迁移后应覆盖全新数据目录、已有管理员、禁用管理员和降权管理员四种启动场景。

- 严重度：P1

## 5. 性能保护策略

所有整改任务统一遵守：

1. 修改前保存 10 次 benchmark 原始输出。
2. 修改后在同机、同 Go 版本、相同 CPU governor 条件下重复采样。
3. 使用 `benchstat` 比较 `ns/op`、`B/op`、`allocs/op`。
4. `ns/op` median 劣化超过 10% 直接回退或重新设计。
5. 内存和分配出现统计显著劣化时，即使耗时未超过 10%，也不得直接合入。
6. Dashboard 对比产物总大小和主入口 gzip 大小，增长超过 5% 必须解释并审批。
7. 正确性、安全性修复不得以降低默认安全级别、跳过校验或扩大缓存为性能换取手段。
