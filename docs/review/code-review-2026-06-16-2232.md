# 存储层性能优化检视报告

时间：2026-06-16 22:32

## 结论

上一轮明确提出并写入 `docs/superpowers/plans/2026-06-16-storage-hotpath-allocation.md` 的优化项已经完成：SSTable index streaming、MemTable reserve 增长策略、compaction 回调分组、value page index streaming、MemTable tableData 复用均已勾选并记录验证结果。

`docs/superpowers/plans/2026-06-16-storage-engine-next-phases.md` 中 Phase 12-18 也均已勾选完成。因此当前没有“计划文档中已承诺但未实现”的存储层优化项。

继续检视存储层后，仍能看到若干更深层的性能优化空间。它们不属于前序任务遗漏，而是下一阶段可以继续压低 RSS、分配、写放大和查询峰值内存的专项。

## 已完成项核对

- 已完成：SSTable index streaming 直读。前台 `Part.Query` / `SeriesIDs` / `QuerySeriesIDs` 已避免全量物化 index rows，字段过滤只保留命中 refs。
- 已完成：MemTable reserve 增长策略。小增量保留受限 slack，大批量写入避免成倍扩容导致 RSS 暴涨。
- 已完成：Compaction 回调式 series group。当前已不再构造 `[][]ColumnData` 分组。
- 已完成：Value page index streaming 读取。热路径不再 materialize `valuePageIndex.Pages`，而是两遍扫描 index payload 并只读取命中 page。
- 已完成：MemTable tableData 复用。`SnapshotAndReset` 后复用 table map，snapshot release 时清理并按上限回池。
- 已验证不适合继续：列对象池化。前序复测显示会抬高 RSS，已撤销。

## 新检视出的优化候选

### P1：Compaction 仍存在 batch 级 `[]ColumnData` 中间集合

证据：
- `writeStreamingCompactionOutputsLocked` 按 256 个 series 分批，但每批仍调用 `queryCompactionSeriesBatch` 返回完整 `[]ColumnData`，随后再 `forEachCompactionSeriesGroup` 排序分组。
- 位置：`internal/engine/lifecycle.go:126`、`internal/engine/lifecycle.go:147`、`internal/engine/lifecycle.go:152`。

影响：
- 在宽表、长时间范围、多个 part 合并时，峰值内存仍与 batch 内命中的列和样本数相关。
- 当前实现已经比 `[][]ColumnData` 低，但还不是“按 series 边读边归并边写”的最低峰值形态。

建议：
- 增加 per-series compaction cursor，按 seriesID 从每个 input part 拉取列。
- 对单个 series 做 merge、tombstone filter、输出写入，然后释放该 series 的临时样本。
- 验收指标：1M wide10 compact RSS 峰值低于当前记录 `151412 KB`，alloc_space 明显低于 `14.49 GB`，输出 SSTable 和查询结果完全一致。

### P1：SSTable value block 解码仍分配 timestamps/writeSeqs/samples 多段切片

证据：
- `readIndexedTimeRefs` 会构造 `[]int64`。
- `readWriteSeqs` 会构造 `[]uint64`。
- `readFloatSamples` / `readIntSamples` / `readBoolSamples` / `readStringSamples` 再构造 `[]VersionedSample`。
- 位置：`internal/sstable/encoding.go:459`、`internal/sstable/encoding.go:503`、`internal/sstable/encoding.go:579`。

影响：
- Page index 已经减少“读多少 page”，但命中 page 内仍有固定的中间数组分配。
- 对窄范围查询和 compaction 都会产生 alloc_space 压力。

建议：
- 设计 streaming decoder：先读取 time refs 与 writeSeq，但直接 append 到目标 `[]VersionedSample`，避免 timestamps/writeSeqs/samples 三段同时驻留。
- 对 bool 解码避免先生成 `[]bool` 再转样本，按 bit 直接输出。
- 验收指标：100K/1M query pprof 中 `readWriteSeqs`、`read*Samples` alloc_space 显著下降，查询结果保持一致。

### P1：WAL batch 格式仍写入重复 identity 字符串，存在写放大

证据：
- `estimatePointSize` 和 `appendPoint` 每个 point 都写入 database、retention policy、measurement、tags。
- 每个 field 还写入 field name。
- 位置：`internal/wal/encoding.go:39`、`internal/wal/encoding.go:250`、`internal/wal/encoding.go:318`。

影响：
- 对 10M wide10 写入，WAL 会重复写大量相同字符串，增加磁盘带宽、编码 CPU 和内存拷贝。
- 当前 SSTable 已较紧密，但 WAL 仍是写入路径上的空间与 CPU 放大来源。

建议：
- 增加 WAL v3 batch：batch 级 string table / series table / field table。
- Point 只写 seriesID、timestamp、writeSeq、fieldID/value，必要时保留首见 series 的 identity。
- 保留 v2 replay 兼容。
- 验收指标：相同 workload WAL bytes/point 降低，replay 结果一致，写入耗时不回退。

### P2：Catalog 多 tag series key 仍排序并拼接字符串

证据：
- 多 tag 路径 `seriesKey` 每次构造 `keys`、排序、拼接 `parts` 并 `strings.Join`。
- batch cache 仍以 string key 保存。
- 位置：`internal/catalog/key.go:8`、`internal/catalog/key.go:17`、`internal/catalog/resolve.go:53`。

影响：
- 对多 tag 高吞吐写入，Catalog.ResolvePoints 仍会产生明显 CPU 和临时分配。
- 当前对 0/1 tag 有快路径，多 tag 仍可继续优化。

建议：
- 引入 canonical tag fingerprint 或 tag-set intern cache，避免每点重复排序和拼接。
- 对同一个 batch 中重复 tags 的点，使用可复用 scratch 构造 key 或直接使用结构化 cache key。
- 验收指标：多 tag 写入 pprof 中 `seriesKey`、`sort.Strings`、`strings.Join` 从热点中下降。

### P2：MemTable 查询仍通过 clone snapshot 构造列集合

证据：
- `MemTable.Query` 调用 `Snapshot()`，而 `Snapshot()` 会 `cloneData`。
- `Snapshot.Columns` 再构造 `[]ColumnData` 并排序。
- 位置：`internal/memtable/memtable.go:99`、`internal/memtable/memtable.go:108`、`internal/memtable/memtable.go:116`。

影响：
- 前台查询与 flush 已经比原始实现稳定，但内存表查询仍会为一致性复制数据。
- 查询并发较高或 MemTable 较大时，临时分配和峰值 RSS 会放大。

建议：
- 增加只读 iterator / RLock 下的 streaming query，或者 MVCC-style immutable column snapshot。
- 对公开 slice API 保持兼容，但内部 merge 优先使用 iterator。
- 验收指标：MemTable-only query 的 B/op 与 allocs/op 下降，读写并发测试无数据竞争。

### P2：Value page index 两遍扫描降低对象分配，但增加 CPU 扫描

证据：
- `readValuePagesFromIndexPayload` 先调用 `matchingValuePageIndexHeader` 统计命中 page，再重新扫描读取 page refs。
- 位置：`internal/sstable/read.go:320`、`internal/sstable/read.go:360`。

影响：
- 两遍扫描避免了 `[]valuePageRef` materialize，是上一轮优化的正确方向。
- 当 pageCount 很大且查询范围较宽时，两遍扫描会产生额外 CPU。

建议：
- 保留当前低内存路径；再增加 query shape 自适应策略：窄查询走两遍，宽查询或全量命中可单遍并使用受限 scratch。
- 验收指标：窄查询 RSS 不回退，宽查询 CPU 时间下降。

### P3：pprof 工具指标还不够完整

证据：
- 当前 pprof 工具输出 SSTable 数、落盘大小、heap alloc/sys。
- 已暴露写入 batch、MemTable、compaction 参数和 `-prebuild-points`。
- 位置：`tests/pprof/storage_engine/main.go:108`、`tests/pprof/storage_engine/main.go:130`。

影响：
- 能定位主要问题，但对 GC 次数、GC pause、RSS peak、alloc_space top 自动摘要仍需手工分析。

建议：
- 输出 `runtime.MemStats.NumGC`、`PauseTotalNs`、`TotalAlloc`、`Mallocs/Frees`。
- 可选读取 `/proc/self/status` 记录 VmHWM/VmRSS。
- 增加固定矩阵脚本，自动对比 baseline。

## 不建议优先做的项

- 不建议立即大范围引入对象池。前序列对象池化已经证明会抬高 RSS；除非 pprof 明确证明对象生命周期短且池上限可控，否则继续池化容易把 Go heap 常驻量做大。
- 不建议为了压缩文件体积牺牲 WAL replay 可维护性。WAL v3 可以做，但必须保留清晰版本边界和兼容测试。
- 不建议继续扩大单个 `MemTableMaxSamples` 作为主要优化手段。它会减少 SSTable 数，但也会自然抬高 flush 前驻留样本和查询 clone 成本，应与 compaction/flush streaming 配套调优。

## 建议下一阶段 EARS 任务

1. 当执行 compaction 时，系统应按 seriesID 逐个拉取、归并、过滤 tombstone 并写入输出 part，从而避免 batch 级 `[]ColumnData` 常驻。
2. 当读取 SSTable value page 时，系统应将解码结果直接写入目标样本切片，从而避免 timestamps/writeSeqs/values/samples 多段中间数组同时存在。
3. 当追加 WAL batch 时，系统应使用 batch 级字典或 series/field 引用，从而减少重复 identity 字符串写放大。
4. 当解析多 tag point 时，Catalog 应复用 canonical tag key 或 fingerprint，从而减少排序、拼接和临时 map/slice 分配。
5. 当查询 MemTable 时，系统应优先使用只读 iterator 或不可变快照视图，从而避免每次查询 clone 整个 tableData。

## 验证说明

本次是只读检视加报告生成，没有改业务代码，也没有重新运行全量测试、e2e 或 pprof。报告结论基于当前计划文档和源码静态检视；涉及性能收益的数值仍需后续专项以 pprof/benchmark 复测确认。
