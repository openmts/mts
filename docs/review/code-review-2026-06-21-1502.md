# 降采样功能商用就绪度检视

## 结论

当前降采样功能已经具备单机规则物化的核心能力，包含 policy 管理、本地二进制 metadata 持久化、窗口聚合、lookback refresh、watermark checkpoint、range backfill、repair、dry-run、调度取消、run timeout、per-policy status、基础 metrics、e2e/fault/scale 入口。

但它还不能严肃声明为“完整商用”。主要原因是高基数窗口内存上限仍不够硬、聚合执行还不是严格流式、dry-run 估算偏乐观、观测指标模型不够标准、端到端故障矩阵和长期压测证据不足，并且目标 rollup 数据生命周期治理仍缺失。

## 已具备能力

- Public API 已覆盖创建、启停、删除、重置、列表、状态、手动运行、range backfill、repair 和 dry-run：`internal/engine/downsample_metadata.go:11`。
- Policy 默认值和兼容性校验已实现，支持 `BatchSize`、`CheckpointInterval`、`RunTimeout`、`PolicyTagName`，并拒绝非兼容覆盖：`internal/engine/downsample_validate.go:54`，`internal/engine/downsample_validate.go:144`。
- Scheduler 已具备 root context cancellation、Close 停止扫描、单 policy 防重入和 run timeout：`internal/engine/downsample_scheduler.go:12`。
- Window planning 已支持 `InitialStartTime`、lookback refresh、advance window 和 bounded 初始窗口：`internal/engine/downsample_executor.go:235`。
- Watermark 已支持按 checkpoint interval 推进，失败时保留最近 checkpoint：`internal/engine/downsample_executor.go:143`。
- Executor 已使用 `QueryColumnIterator` 获取聚合结果，并按 `BatchSize` 分批写目标 RP：`internal/engine/downsample_executor.go:77`，`internal/engine/downsample_executor.go:104`。
- 目标点已写入 policy tag，便于区分物化来源：`internal/engine/downsample_executor.go:517`。
- Downsample metadata 已落本地二进制文件 `downsample.bin`，没有使用 JSON 存储：`internal/catalog/downsample.go:17`，`internal/catalog/downsample.go:80`。
- Scale 用例已支持 points、series、policy count、batch size、checkpoint interval、run timeout、initial start 和 JSON 报告：`tests/scale/downsample_policy/main.go:103`。
- Fault 用例已覆盖目标写失败后的 health degraded 和 watermark 保留：`tests/fault/downsample_policy/main.go:54`。

## 仍需补齐的商用差距

### P0: 高基数窗口仍存在内存峰值风险

`runDownsampleWindow` 虽然使用 `QueryColumnIterator`，但 `downsampleIteratorToPoints` 仍把一个窗口内的所有输出点收集到 `map[string]*model.Point`，最后再排序成完整 `[]model.Point` 写入：`internal/engine/downsample_executor.go:407`，`internal/engine/downsample_executor.go:538`。

影响：

- `BatchSize` 只限制最终写入批次，不限制聚合输出生成阶段的内存峰值。
- 单窗口内 group cardinality 很高时，内存仍与 `窗口内 group 数 * 聚合字段数` 成正比增长。
- 这与“后台降采样不能明显抬高引擎 RSS”的商用要求仍有差距。

建议：

- 将 executor 改为按 group/window 有序流式输出，或至少对 `byKey` 做 bounded flush。
- 需要保证同一输出点的多个聚合字段完整合并后再写入，避免同 timestamp/tag 被拆成多个不完整点。
- 对高基数窗口新增 RSS 上限回归用例。

### P0: Group aggregate 仍会 materialize 当前查询的全部 group accumulator

`groupAggregateColumnStream.load` 会把源列全部读入 `accumulators`，然后一次性 `materializeGroupAccumulators` 到 `pending`：`internal/queryexec/group_aggregate.go:88`，`internal/queryexec/group_aggregate.go:168`。

影响：

- 降采样使用了 iterator，但底层 group aggregate 仍是窗口级 materialize，不是严格流式 group aggregate。
- 超大窗口或高基数 group 场景下，查询执行器自身会先形成内存峰值。

建议：

- 查询执行器需要支持按时间窗口和 group key 的增量输出。
- 如果当前 SSTable/iterator 顺序暂不能保证全局有序，应先做 bounded partition 或 spill 策略。

### P0: 缺少长期 1M/10M 压测结果作为商用证据

`tests/scale/downsample_policy` 默认规模为 100K 点，且当前检视只确认了参数化入口，没有看到已落盘的长期 1M/10M 报告：`tests/scale/downsample_policy/main.go:18`。

影响：

- 不能证明后台降采样在目标数据规模下的 RSS、CPU、GC、磁盘放大、查询准确性和恢复耗时。
- 不能给出明确的默认参数建议，例如窗口大小、batch size、checkpoint interval、policy count 上限。

建议：

- 固化 100K、1M、10M 三档压测脚本和报告。
- 报告至少包含 write/downsample/query duration、RSS peak、CPU profile、alloc profile、GC 次数、磁盘空间、SSTable 数、输出点数、校验通过率。

### P1: Dry-run 的目标点估算明显偏乐观

`DryRunDownsamplePolicy` 的 `PointsEstimate` 目前等于窗口数量：`internal/engine/downsample_metadata.go:154`。

影响：

- 真实目标点数量大致应是 `窗口数 * group cardinality`，还与 group tag、字段函数数量、过滤条件有关。
- 用户用 dry-run 评估 backfill 成本时会严重低估高基数任务风险。

建议：

- dry-run 至少返回窗口数、估算 group 数、估算输出点数和估算读样本数。
- 可先通过 source metadata/series index 估算，估算不可得时明确标记 unknown，而不是给出低估值。

### P1: Metrics 模型不够标准

per-policy metrics 通过 policy name 拼到 metric name 中，例如 `mts_downsample_policy_<policy>_lag_seconds`：`internal/engine/metrics.go:135`。

影响：

- policy 多时会产生大量 metric name，不利于 Prometheus 侧的稳定采集和聚合。
- 标准做法应使用固定指标名加 label，例如 `mts_downsample_policy_lag_seconds{policy="cpu_1m"}`。

建议：

- 扩展 observability registry 的 label 能力。
- 将 per-policy 指标迁移到固定 metric name + label。

### P1: MetricsSnapshot 静默忽略 status 读取错误

`MetricsSnapshot` 调用 `DownsamplePolicyStatuses(context.Background(), now)` 后忽略错误：`internal/engine/engine.go:470`。

影响：

- metadata 读取失败时，per-policy 指标会静默缺失。
- 运维侧难以区分“没有 policy”和“status 读取失败”。

建议：

- 记录 downsample status 采集错误指标。
- HealthSnapshot 中体现 metrics/status 采集失败。

### P1: 端到端 fault 矩阵仍不完整

public fault 用例目前主要覆盖目标写失败：`tests/fault/downsample_policy/main.go:54`。metadata 保存失败、fsync/rename 失败、query cancellation、reset replace、异常关闭后恢复等更多场景主要在 unit 层或尚缺 e2e 组合验证。

影响：

- 商用场景中，后台任务最容易暴露在掉电、磁盘满、metadata 更新失败和重复运行中。
- 仅有 unit fault 不足以证明完整引擎生命周期下的恢复行为。

建议：

- 扩展 `tests/fault/downsample_policy`，把 metadata fault、context cancel、engine close、restart recovery、policy replace/reset 纳入端到端矩阵。
- 每个 fault case 验证 watermark、target data、health、metrics 和可重跑性。

### P1: 目标 rollup 数据缺少生命周期治理

`ResetDownsamplePolicy` 只调整 watermark 和替换许可，不删除或隔离旧目标数据：`internal/engine/downsample_metadata.go:43`。`DropDownsamplePolicy` 只删除 policy 和 watermark，不清理目标 RP 中已物化数据：`internal/engine/downsample_metadata.go:36`。

影响：

- policy 函数、group tag、target 变更后，旧 rollup 数据可能继续存在。
- repair/backfill 重算同一窗口时，如果写入语义不是严格覆盖，可能产生重复或混合结果风险。

建议：

- 明确目标数据写入幂等语义：同 measurement/tags/timestamp 的字段覆盖或合并策略。
- 提供按 policy tag 清理目标 rollup 数据的维护 API。
- reset/drop 时至少提供可选 cleanup 方案。

### P1: 降采样函数集合仍偏窄

当前支持 `avg/min/max/sum/count/first/last`，并将 `mean` 归一到 `avg`：`internal/engine/downsample_validate.go:20`，`internal/engine/downsample_validate.go:88`。

影响：

- 与 InfluxDB、VictoriaMetrics、Prometheus recording rule、Timescale continuous aggregate 等成熟系统相比，常见 rollup 能力仍不足。
- `rate`、`irate`、`difference`、`mode`、`percentile/quantile`、`stddev` 等没有进入降采样 policy。

建议：

- 分层扩展函数：先补可精确窗口计算的 `difference/mode/stddev`，再评估 `rate/irate/quantile` 的语义和边界。
- 对 counter reset、缺点、乱序和类型约束定义清楚后再实现。

### P2: 尚无自动 rollup 查询路由

项目当前明确不做 SQL parser 和自动查询路由，降采样结果由用户显式查询目标 retention policy。该设计符合当前项目边界，但从商用体验看仍是差距。

影响：

- 用户需要自行选择 raw RP 或 downsample RP。
- 查询层不能根据时间范围、精度和 policy 自动选择更低成本的数据源。

建议：

- 若未来进入产品化阶段，可在 Builder 层提供显式 `UseDownsample(policy)` 或 `PreferDownsample(interval)`，不必引入 SQL parser。

### P2: 未做 compaction/page-level rollup

当前实现是规则驱动的后台查询写入，并未在 compaction 或 SSTable page metadata 层生成 rollup。

影响：

- 大规模历史 backfill 成本高于存储层内建 rollup。
- 对非常长时间范围聚合查询，仍依赖已物化 policy 或普通查询执行器。

建议：

- 当前阶段可接受；若目标是接近成熟 TSDB 的长期历史查询效率，需要独立设计存储层 rollup metadata 或 page stats。

## 总体判断

当前实现适合单机受控环境的 beta/RC 级试用：可以创建 policy、物化聚合结果、恢复水位、运行 repair/backfill，并具备基本观测和运维入口。

距离“可商用”还差至少三类硬证据和硬能力：

1. 高基数窗口下的内存上限控制。
2. 长期 1M/10M 压测和故障矩阵证据。
3. 目标 rollup 数据生命周期和观测标准化。

在这三类问题闭环前，不建议对外声明降采样功能已达到完整商用。

## 2026-06-21 处理状态

- P0 高基数窗口输出内存风险：已处理。executor 改为源列扫描和窗口内聚合，删除旧的 query aggregate 输出合并路径，目标点按 `BatchSize` 写入。
- P0 group aggregate materialize 风险：已缓解。降采样主路径不再依赖 `NewGroupAggregateColumnStream` 产生中间聚合列，序列函数只保留必要窗口内样本。
- P0 长期压测证据不足：已补入口。scale report 增加 heap、GC、disk bytes、SSTable count；长期 1M/10M 报告仍需在实际压测执行中沉淀数据。
- P1 dry-run 估算偏乐观：已处理。dry-run 返回 group、sample、point 估算。
- P1 metrics 模型不标准：已处理。per-policy metrics 改为固定 metric name + `policy` label。
- P1 status 采集错误静默：已处理。`MetricsSnapshot` 增加 status collection error 指标。
- P1 fault 矩阵不完整：已补核心单元覆盖并保持 fault e2e 通过。metadata/write/cancel/reset replace 仍主要由 engine unit 覆盖。
- P1 目标 rollup 数据生命周期治理：已处理。新增 drop/reset cleanup 选项，按 policy tag 对目标数据写 tombstone。
- P1 函数集合偏窄：已处理。policy 支持 `rate/irate/increase/delta/difference/derivative/spread/mode/stddev/stdvar/top/bottom/median`。
- P2 自动 rollup 查询路由：已按项目边界处理。新增 `QueryBuilder.FromDownsamplePolicy(policy)` 作为显式 Builder 查询入口，不引入 SQL parser 或自动路由。
- P2 page-level rollup：已文档化边界。当前专项不改 SSTable 格式，后续如需要应单独开持久化格式专项。
